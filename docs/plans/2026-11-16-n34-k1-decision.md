### 2.2 추론 (코드 읽기 기반, 측정으로 확정되지 않음)
- I-1: F1(CR만 10 MiB)에서 pre-K1은 lone CR마다 빈 줄을 만든다. main은 lone CR을 나누지 않는다
  - 그래서 pre-K1은 빈 줄 10,485,761개마다 두 predicate 본문을 실행한다: 5개 predicate 배열 생성, `trim().split().filter()` 등
  - 이것이 F-2 증가의 유력한 작업량 차이다. 원인 확정은 아니다(run3 최종 검토도 같은 표현)
- I-2: K1은 그 본문 작업을 없앤다. 빈 줄마다 남는 것은 문자 스캔, `slice`, 콜백·함수 호출, 길이 비교다
  - F4·F3(LF·CRLF 빈 줄)에서도 같은 본문 작업이 사라진다
  - F-5의 같은 run 관찰이 같은 방향이다
- I-3: K1의 공개 결과 위험은 B와 같은 수준이다(F-11). A와 B의 차이는 기능이 아니라 성능 근거와 F1 위험이다
- I-4: K1 대 pre-K1 증분 gate PASS와 run3(pre-K1 대 main) PASS를 합쳐도 K1 대 main 판정이 되지 않는다
  - 각 gate는 median 1.10배까지 허용하므로 두 비율을 곱하면 1.10배를 넘을 수 있다
  - 서로 다른 run의 비율 곱은 금지다. 따라서 K1(또는 C) 코드로 N34 종료 gate를 주장하려면 **그 코드 대 main 직접 공식 run**이 필요하다
  - 비교 기준 코드를 main으로 맞추는 것과 입력을 같게 만드는 것은 별개다(F-15)
    - 그 run의 필수 PASS는 F1에 대해 CR 대 LF 비교만 보장한다
    - F1 same-input 위험(F-2)의 크기는 정보용 블록 결과로만 관찰된다. 필수 블록이 pass하지 않으면 그 결과는 아예 없다

## 4. C 후보 (현재 source 기준, 설계 승인 전)
- 공통 의무
  - 공개 `classifyContext` 결과(mode·reasons 순서·warnings)와 `lossyCompressionAllowed`가 pre-K1과 같아야 한다
  - `somePolicyLine` 자체의 계약(F-13)은 바꾸지 않는다
  - 보안·분류 규칙을 줄이거나 우회하지 않는다(K2·classify 우회 금지 유지)
- **C1 비어 있지 않은 줄 전용 순회**
  - 두 호출자([L793, L797][src-policy])만 새 private helper를 쓴다
  - 새 계약: `split(POLICY_LINE_BREAK).filter(l => l.length > 0).some(p)`와 호출 접두열·예외 전파가 같다
  - `somePolicyLine`과 그 테스트는 그대로 둔다. 빈 줄 호출을 일반 helper에서 생략하면 F-13 계약과 충돌하므로 그렇게 하지 않는다
  - 결합 증명: 두 predicate는 `""`에 false이고(F-10), 관측 가능한 부수효과가 없다(lastIndex는 F-12로 재초기화)
  - 기계적 절감: 빈 줄당 `slice`·콜백·호출. K1이 이미 본문을 없앴으므로 추가 이득은 작을 수 있다(U-4)
- **C2 두 순회 통합**
  - [L649–L654][src-policy]의 두 전체 순회를 한 번으로: 줄마다 `isShellCommandLine(line) || hasTechnicalTokenShape(line)`
  - 정상 경로 결과는 같다. 둘 다 `code_or_path` 하나를 같은 자리에 넣는다
  - **증명 의무(미확인 위험):** 호출 순서가 "셸 전체 → 기술 전체"에서 줄 단위 교대로 바뀐다
    - 그런 입력이 실제로 있는지는 확인하지 않았다. 구체적 반례도, 불가능하다는 증명도 없다
    - 만약 어떤 입력에서 한 predicate가 RangeError 등 예외를 던지고 다른 predicate가 앞 줄에서 true를 낸다면, 결과가 달라질 수 있다
      - RangeError라면 `classification_resource_limit`([L687–L696][src-policy])과 exact 판정 사이에서 달라진다
      - 다른 예외라면 전파 여부 자체가 달라진다
    - C2를 고르려면 그런 입력이 없다는 증명, 또는 차이를 없애는 설계가 필요하다. 둘 다 없으면 공개 계약 변경이며 사용자 승인 대상이다
  - 기계적 절감: 10 MiB 문자 스캔 1회와 줄 `slice` 1벌
- 기각 후보
  - EXACT_PATTERNS가 이미 `code_or_path`를 넣었을 때 두 순회를 생략하는 안: resource-limit 결과가 바뀌고, F1에는 해당 reason이 없어 효과도 없다
  - CR 전용 입력 조기 판정: 분류 정책 우회라 금지
- 측정 유효성 문제(U-1, U-3)는 C로 해결되지 않는다. C도 A와 같은 O2 A/A 취약성 아래에서 공식 gate를 통과해야 한다

  1. K1은 공개 결과가 pre-K1과 같다(F-11). A와 B 중 고르는 기준은 기능이 아니라 성능 근거와 F1 위험이다(I-3)
  2. B는 측정된 F1 증가를 알고 남긴다. 그 작업량 차이(I-1)를 직접 겨냥한 최소 변경이 이미 있다. 같은 run 유효 행에서 같은 방향 관찰도 있다(F-5)
  3. 사용자는 기간보다 완성도를 우선한다. 그 기준에서 "검증된 코드 + 알려진 회귀 수용"보다 "검증된 코드 + 회귀 축소 근거"가 더 완성된 끝 상태다
     - 이 끝 상태는 **유효한 공식 run과 정보용 F1 same-input 근거가 모두 확보될 때만** 도달할 수 있다
     - A는 그 근거를 얻으려는 가장 작은 변경 경로일 뿐이다. 도달을 보장하지 않는다
  4. C는 K1 뒤 남은 비용이 중요하다는 근거(U-4) 없이 동치 의무와 회귀 면적을 늘린다
  5. A를 먼저 고르면 B로 갈 길이 남는다. 실패 시 B로 가는 변경은 기계적 revert다. 반대로 B 뒤 A로 오려면 새 결정과 같은 공식 run이 다시 필요하다
- 반대 근거 (추천을 약하게 만드는 사실)
  - A의 남은 문제는 두 가지다
    - 측정 유효성(U-1). D1은 이를 해결하지 못했다. N34 공식 run 4회 중 PASS는 1회다(F-9)
    - main 대비 timing·memory·F1 same-input 미측정(U-2)
  - run3 PASS도 O2/F3 경계값이었다(F-7). A의 P10은 다시 INVALID가 될 수 있다
  - 필수 PASS여도 F1 same-input은 정보용이다(F-15). 감소가 관찰되지 않거나 무효·미실행일 수 있다
    - 그 경우 A의 끝 상태는 "K1 유지 + F1 위험 수용"이 된다. 위험 측면에서는 B와 같다
  - A는 K1 대 main run3 규모(K1 prereg §7의 run3 기준 추정 timing 약 3.8시간 + memory + 정보용 블록, PC 독점)가 필요하다. 증분 K1 run 재실행만으로는 부족하다(I-4)
  - F1은 내용 없는 CR 10 MiB라는 최악 형태다. 내용 있는 CR 입력(F2·F7)은 정보용 한계 안이었다(F-3). 실사용 영향은 작을 수 있다
  - 그래서 B도 정직한 선택이다. B는 이미 유효한 근거만으로 끝난다
- 결정이 B로 바뀌는 조건
  - 사용자가 내용 없는 CR 밀집 입력의 시간 증가를 비목표로 보고 위험을 수용한다
  - P10-A 계획 PR의 preflight에서 primary가 "O2 A/A 유효성 대응이 설득력 없음"으로 판정한다
  - P10-A 공식 run이 INVALID이거나 유효 FAIL이다
  - P10-A 정보용 F1 same-input이 과다·무효·미실행이고, 사용자가 사전 절차에 따른 위험 수용을 하지 않는다(중단·재결정)
- 결정이 C로 바뀌는 조건
  - 승인된 profiling 등으로 K1 뒤 남은 빈 줄당 비용이 F1 증가의 주된 몫임이 보인다
  - 또는 A의 필수 G-C F1 행(CR 대 LF)이 유효 FAIL이다
