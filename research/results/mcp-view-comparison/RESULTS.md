# 제품 MCP 원본·개요·영역 보기 비교: 결과

- 프로토콜: [`research/plans/2026-11-23-mcp-view-comparison-protocol.md`](../../plans/2026-11-23-mcp-view-comparison-protocol.md)
- 기준 `41fc769`. 번들 blob `5709a18`
- 알려진 자료를 재현한 **기술적 비교**다. 확인적 검정이 아니다
  - RGB 인코딩 통제와 고정 호출자는 사후 설계다
  - 금표준은 R09에서 이미 공개되었다
  - OCR은 다시 돌리지 않았고, 저장된 R09 선택 결과를 재생했다
- 기술 빈도와 원시 분모만 보고한다
- 측정한 것은 원본 픽셀 공간의 **기하적 포함**뿐이다
  - 판독성(축소 뒤 글자를 읽을 수 있는지)과 모델 정답률은 모든 조건에서 미측정이다
  - 호출·읽기 횟수는 기계 규칙의 결과다. 사람이나 모델의 행동이 아니다

## 1. 주요 관측 (셀마다 분모 48, 키 576)

| 표현 | 프로필 | 보기 | 색인 수락 | 반환 | 근거 포함 complete/partial/평가불가 |
|---|---|---|---|---|---|
| 회색조 원본 | strict | 원본·개요·영역 | 각 0/48 | 없음 48 | 0/0/48 |
| 회색조 원본 | tolerant | 원본·개요·영역 | 각 0/48 | 없음 48 | 0/0/48 |
| RGB 파생 | strict·tolerant | 원본 | 48/48 | 원본 참조, 실제 열어 검증 48 | 48/0/0 |
| RGB 파생 | strict·tolerant | 개요(512) | 48/48 | 개요 JPEG 512×384, 디코드 48 | 48/0/0 (전체 시야. 판독성 미측정) |
| RGB 파생 | strict·tolerant | 영역 | 48/48 | 부분 JPEG 36, 원본 참조(폴백) 12 | 47/1/0 |

- **회색조 거부.** R09 원본 48장(PNG 8-bit, color type 0)은 두 프로필 모두 `index_image_artifact`에서 `unsupported_png_profile`로 거부되었다(6셀 × 48 = 288행)
  - 후속 도구는 호출하지 않았다(`not_called`)
  - 이 행들은 분모에 남고, 근거 포함은 평가 불가다
- **RGB 수락.** 픽셀이 같은 무메타데이터 RGB 파생본(IHDR·IDAT·IEND만)은 두 프로필 모두 48/48 수락되었다
  - strict: `png-rgb8-static-v1`
  - tolerant: `png-rgb8-tolerant-v1`, `ignoredChunks: []`
  - strict와 tolerant의 결과가 같다
- **원본 보기.** `crop_image_artifact`에 전체 좌표를 주면 인코딩 없이 `status: original`, `fullFrame: true`와 원본 참조(`source.path`)를 돌려준다
  - 호출자가 그 경로를 실제로 열어 RGB 기대 SHA와 대조했다. 96행(2 프로필 × 48) 모두 일치했다
- **개요.** `maxSide=512`에서 1280×960 → 512×384이다. 규칙상 기대값, 응답 치수, sharp 실제 디코드 치수가 모두 같았다(192행 = 개요 96 + 영역 경로의 개요 96)
- **영역**(R09 좌표 재생)

  | 언어 × 앵커 | 매치 → 부분 JPEG | 미매치 → 원본 참조(폴백) | complete | partial |
  |---|---|---|---|---|
  | EN·code | 12 | 0 | 12 | 0 |
  | KO·code | 12 | 0 | 11 | 1 |
  | EN·nl | 12 | 0 | 12 | 0 |
  | KO·nl | 0 | 12 | 12 | 0 |

  - KO·nl 12건은 모두 미매치(한국어 질문에 ASCII 키가 없음)였다. 폴백으로 원본 참조를 새로 요청하고 실제로 읽었다. 근거는 전체 시야라 포함되지만, 영역을 줄이는 효과는 없다
  - partial 1건: `status-cards-code-s1-ko`(두 프로필 모두)
    - 반환 영역 `[608, 865) × [0, 525)`. 답 값 잉크 `r3v`는 `[842, 867) × [421, 439)`로 오른쪽 경계를 **2px** 넘었다
    - 응답은 요청 영역을 그대로 돌려주었고, 잘림을 알리는 신호가 없다
    - 호출자도 금표준 없이는 잘림을 알 수 없으므로 재조회는 0회였다. **검출되지 않은 누락**으로 기록한다
  - 짝 표(24쌍): both 23, EN만 1, KO만 0, neither 0. 두 프로필 같다

## 3. 재현과 검증

- 실행 A와 B(같은 작업 사본, CRLF)의 결정적 출력이 바이트 단위로 같았다: `raw.jsonl`, `cells.jsonl`, `input-check.json`, `score.json`, `summary.md`
- 실행 C(`core.autocrlf=false`로 꺼낸 LF 사본)도 A와 바이트 단위로 같았다
  - 같은 파일: 위 출력 전부와 준비 산출물(`assignment.json`, `expected-sha.json`, `prepare-report.json`)
  - 번들 작업 사본의 원바이트 SHA는 CRLF `9fa0bf7a…`, LF `6265b9b4…`로 다르다. Git blob은 둘 다 `5709a184…`다. 입력은 기준 커밋 blob에서 읽으므로 줄바꿈과 무관하다
- 세 실행의 `evidence.json`이 같다
- Python 독립 검산(`tools/mcp-view-comparison-recount.py`, run-b 원시값과 score-a 대조): 행 576, 셀 12, 불일치 0
- 오프라인 가드: 실행마다 가드 이벤트 13개(실행기 1 + 셀 12), 차단 0. API 키를 넘기지 않았다
- RGB 파생: 같은 환경에서 두 번 파생한 manifest가 바이트 단위로 같았다. 실행 전 검산은 두 가지로 했다: 파생기의 Pillow 비교와 실행기의 자체 PNG 디코더 비교. 48장 모두 각 채널이 원본 밝기면과 같았다

## 4. 한계

- 합성 문서 48장(1280×960)뿐이다. 실데이터와 다른 해상도·형식에는 일반화하지 않는다
- 금표준이 공개된 뒤의 재사용이다. 호출자 조건은 결과를 보기 전에 고정했지만, 사후 설계라는 점은 그대로다
- OCR 없이 R09 선택 결과를 재생했다. 선택기 자체의 재현성은 R09 PR #140의 기록에 의존한다
- 개요의 complete는 전체 시야를 담았다는 기하적 사실일 뿐이다. 512×384로 줄인 뒤의 판독성은 측정하지 않았다
- 바이트 크기와 호출 수를 청구 토큰이나 비용으로 바꾸지 않는다
- PNG 압축 바이트는 Pillow·zlib 빌드에 따라 달라질 수 있다. 기록한 환경: Pillow 12.3.0, zlib 1.3.1.zlib-ng, Python 3.12.10
- 채점 입력 분리는 입력 폴더 허용 목록, 이름 검사, 실행기 소스 정적 검사, 동결 해시 순서로 보장한다. OS 수준 격리는 아니다. 실행기는 저장소 안에서 돌고 번들 확인에 git을 부른다
- 클라이언트는 시간 초과 뒤 늦게 온 응답과 해석할 수 없는 출력 줄을 세지 않는다. 이번 실행에서는 12셀 모두 요청 수와 응답 수가 같아 해당 사례가 없다
- 테스트의 RED는 하네스 모듈이 없어 생긴 import 실패였다. 각 테스트가 특정 결함을 잡는다는 변이 검증은 하지 않았다. 마일스톤 검토 수정에서 더한 6개 테스트도 수정 전에는 새 export 부재로 import 단계에서 실패했다(개별 테스트 단위 실패는 확인하지 않았다)
