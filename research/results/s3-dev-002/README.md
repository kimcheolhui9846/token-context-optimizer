## 개발 단계에서 고친 것 (calibration 전에 고정)

1. **도구 결과 이미지 비우기(EVICT).** s3-dev-001에서 S2는 S0보다 토큰을 줄이지 못했다(33,352 대 34,032).
   도구 왕복으로 호출 수가 늘었고, 도구가 돌려준 crop·원본 이미지가 기록에 계속 쌓였기 때문이다.
   턴이 끝나면 도구가 돌려준 이미지를 기록에서 지우고 짧은 설명만 남기게 하자, 입력 토큰이 18,756으로 줄었다(S0 대비 −45%).
2. **원본 자동 재요청(AUTO_ORIGINAL).** s3-dev-001에서 모델은 지시와 달리 원본을 거의 요청하지 않고 UNREADABLE로 답했다.
   플러그인 조건에서 답이 UNREADABLE이면 하네스가 마지막으로 조회한 이미지의 원본을 주고 한 번 더 묻게 했다(pilot-003 C1R과 같은 규칙).
3. **채점 규칙.** yes/no·on/off는 정확히 일치해야 맞다. 숫자 정답은 응답 안의 숫자와 같아야 맞다. 월 약어는 전체 이름도 맞다(Sep = September).
   s3-dev-001의 첫 채점은 "September"를 "Sep"의 오답으로, 첫 수정본은 "$15,108.11"을 오답으로 잘못 처리했다. 두 경우를 고쳤다.

## 관찰 (개발 세트, 근거 아님)

- **compact 모사는 세부를 잃었다.** S1은 토큰을 절반으로 줄였지만, 요약에 남지 않은 세부를 묻는 턴에서 UNREADABLE로 답했다. 늦은 회상은 78%에서 44%, 교차는 67%에서 33%로 떨어졌다. 가설 H2의 방향이다.
- **원본 보존 발췌는 정확도를 유지하며 토큰을 줄였다.** S2는 S0와 같은 정확도(79%), 같은 늦은 회상(78%)에서 정가 기준 입력 토큰 −45%였다. 가설 H1의 방향이다.
- **캐싱이 절감 폭을 줄였다.** 이미지를 비우면 기록의 앞부분이 바뀌어 공급자 캐시 접두부가 깨진다(S0 캐시 18,773 대 S2 2,645). 캐시 기준으로는 S2의 절감이 −25%로 줄었다. compact도 마찬가지로 캐시를 깬다. "기록 편집과 프롬프트 캐싱의 충돌"은 가설 H4를 넘어서는 별도 관찰이다.
- **S4(1536 축소)는 GPT-4o 토큰을 줄이지 않았다.** RQ1의 회계 결과(pilot-001)와 같다.
- **S3는 이번 설계에서 S2와 구별되지 않았다.** 플러그인 조건은 컨텍스트가 작아 임계값(4,000)을 넘지 않았고 compact가 한 번도 일어나지 않았다. H3(플러그인이 compact 뒤의 회상을 되찾는가)를 시험하려면 설계를 바꿔야 한다(아래).
- 남은 오류는 13px 작은 글자 오독(INV-59162-E를 69162로, 7924를 71924로)과 에이전트가 엉뚱한 이미지를 조회한 경우다. 원본을 다시 받아도 작은 글자를 읽지 못한 경우가 있었다. 파일럿의 "원본은 작은 글자에 안전하지 않다"와 같다.

## calibration 전에 정할 것

- **compact 시점(제안).** 임계값 방식은 컨텍스트가 작은 플러그인 조건에서 compact를 일으키지 않는다. 그 자체가 플러그인의 이점(손실 요약 횟수 감소)이지만, H3를 시험할 수 없다.
  제안: S1과 S3 모두 **턴 3과 턴 6 뒤에 compact하는 고정 일정**을 주 설계로 쓴다. 그러면 두 조건이 같은 시점에 손실 요약을 겪고, 차이는 아티팩트를 다시 꺼낼 수 있는지뿐이다. 임계값 방식으로 "compact가 일어났을 횟수"는 보조 지표로 보고한다.
- 위 규칙(EVICT, AUTO_ORIGINAL, 채점, compact 시점)을 고정한 뒤 calibration 6세션을 실행한다.
