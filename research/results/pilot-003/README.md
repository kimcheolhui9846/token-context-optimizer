## 관찰 (탐색 수준)

1. **주 비교 결과: C1R은 원래 해상도 조건에서 A와 같은 정확도를 토큰 25% 적게 얻었다.**
   clean에서 89% 대 89%(짝지은 비교에서 C1R만 맞힘 1, A만 맞힘 1), 616 대 825 토큰.
   JPEG-only에서는 89% 대 86%(2 대 1), 621 대 825 토큰. 차이 1–2건이라 정확도 우열은 말할 수 없다.
2. **창 selector(C1)는 crop 면적을 줄여 토큰을 28% 줄였다.** pilot-002의 띠 selector(dev2, −15%)보다 큰 감소다.
   다만 세트가 달라 직접 비교는 아니다. C1이 근거를 덮었을 때 95%(71/75)를 맞혔다.
3. **응답 기반 fallback은 오경보 없이 작동했지만 일부만 잡았다.** C1의 UNREADABLE 12건은 모두 근거를 놓친 경우였다
   (덮은 경우 0건). 근거 상자를 다 덮지 못한 28건의 구성은 맞힘 12건(답이 창 안에 있었다), UNREADABLE 12건, 다른 값 4건이다.
   C1의 틀린 답 가운데 판독 불가로 표시되지 않은 것이 28건(144건 중)이며, 행을 못 찾아 전체 프레임을 보낸 경우와
   1024 조건의 오독을 포함한다. 이 "조용한 오답"이 남은 위험이다.
4. **1024 조건에서는 selector가 여전히 A보다 나쁘다.** OCR이 작은 글자를 놓치기 때문이다(downscale-only C1R 75% 대 A 86%).
   해상도를 이미 잃은 입력에는 selector를 쓰지 않는 규칙(예: 입력 해상도로 판단)이 필요해 보인다.
5. **2단계 selector(C2)는 이번 구현에서 실패했다. 다만 방식보다 구현 문제다.** 1단계 144건 중 65건에서 쓸 수 있는 좌표를
   얻지 못했다. 모델이 좌표 대신 답을 말하거나("The total amount on the invoice is …"), 좌표가 뒤집혔거나, 60토큰 상한에서
   JSON이 잘렸다. 좌표를 얻은 79건 중 근거를 덮은 것은 45건이었다. 덮었을 때 정확도는 76%(34/45)였다.
   detail low(512px)에서는 작은 글자 위치를 정확히 찾기 어렵다. C2R은 정확도는 높지만(clean 92%) 토큰이 A보다 18% 많다.
6. **회계 일치 유지.** 단일 호출 arm(A, C1, E)의 이미지 토큰은 이번에도 질문마다 공식과 정확히 일치했다.

## 다음 단계 제안

- **방법 후보를 C1R 계열로 좁힌다.** 원래 해상도 입력에서 정확도를 유지하며 토큰을 25% 줄였다. oracle E(토큰 −49%, 정확도 100%)와의
  격차가 남은 개선 여지다.
- **조용한 오답 줄이기:** 답 형식 검사(질문이 숫자·시간을 묻는데 답이 다른 형식이면 재요청), 창 크기 확대, 질문과 행의
  매칭 점수가 낮을 때 재요청 등. 이 규칙은 다음 실행 전에 정한다.
- **C2를 다시 시험할지:** 구조화 출력(JSON schema), 더 큰 출력 상한, 좌표 검증을 넣으면 공정한 시험이 된다. 비용 구조상
  (1단계가 고정 비용) C1R보다 토큰이 적기는 어렵다. 우선순위는 낮다.
- **두 번째 공급자:** Anthropic 결제 뒤 같은 dev3 slot을 Haiku로 실행한다(C2 제외).
- **본 실험 전 사용자 결정:** guard를 응답 기반 fallback으로 바꾸는 프로토콜 개정, selector 사용 조건(해상도), held-out 규모.
