## 관찰 (탐색 수준)

1. **회계 일치는 이번에도 유지됐다.** 질문 36개 모두에서 "실측 − 타일 공식 예측"이 질문마다 하나의 상수였다(720회).
2. **원래 해상도에서 crop은 정확도와 비용을 동시에 개선했다.** clean에서 E는 A보다 정확도가 11%p 높고(100% 대 89%,
   짝지은 비교에서 E만 맞힌 경우 4, A만 맞힌 경우 0) 토큰은 49% 적다. 13px 글자가 A에서는 provider 축소 때문에 약 6.5px로
   들어가지만, crop은 원래 해상도로 들어가기 때문이다. 예: 알림 배지 "73"을 A·B·C·D는 13, 75, 7 등으로 읽었고 E만 맞혔다.
3. **이미 해상도를 잃은 입력(1024 조건)에서는 crop도 복구하지 못한다.** downscale-only와 combined에서 E는 A와 같거나 같은 수준이다.
4. **현실적인 selector(C)의 병목은 근거를 찾는 능력(recall)이다.** C가 근거를 덮은 83건 중 80건(96%)을 맞혔고,
   놓친 20건은 하나도 맞히지 못했다. 실패의 대부분은 차트다. 막대 값 질문에서 월 이름 행만 잘라 값이 빠졌고,
   "가장 높은 막대" 질문에서 제목 행을 골랐다. 전체 폭 띠 crop은 표·UI 행에는 맞지만 세로 관계가 있는 차트에는 맞지 않는다.
   1024 조건에서는 OCR이 작은 글자를 놓쳐 C가 A보다 크게 나빴다(downscale-only에서 A만 맞힌 경우 9, C만 0).
5. **지금의 guard(OCR 불확실 → 원본)는 거의 효과가 없었다.** fallback 43건 중 41건이 "행을 못 찾은" 경우였는데,
   이때 C도 이미 전체 프레임을 보내므로 D와 C의 입력 차이가 작다. guard가 막아야 할 실패(엉뚱한 행을 고른 20건)는
   20건 모두 guard를 통과했다. OCR confidence로는 이 실패를 구별하지 못했다. 프로토콜이 예상한 대로 D−C의 정보량은 fallback 수에 달려 있었다.
6. **모델의 "UNREADABLE" 응답이 selector 실패를 정확히 표시했다.** C의 UNREADABLE 16건은 모두 근거를 놓친 경우였고,
   근거를 덮은 경우에는 0건이었다. 사후 시뮬레이션: C가 UNREADABLE이면 같은 slot의 A 응답을 쓰는 규칙("응답 기반 fallback")을
   기존 응답으로 계산하면 clean에서 정확도 92%, 평균 토큰 743이다(A는 89%, 824). 별도 호출을 합친 사후 계산이며,
   이 규칙을 미리 정해 실행한 결과가 아니다.
7. **원본 fallback이 작은 글자에 "안전한" 경로가 아니다.** GPT-4o는 큰 원본을 768 짧은 변으로 줄여 처리하므로,
   작은 글자에서는 원본이 오히려 손실이 큰 경로다. 프로토콜의 "보수적 원본 fallback" 전제를 공급자 처리 방식과 함께
   다시 검토해야 한다.

## 연구 방향에 주는 함의 (제안, 사용자 결정 사항)

- **방법의 핵심을 "원래 해상도 영역 crop"으로 둔다.** oracle 상한은 크고(clean +11%p, 토큰 −49%), 현실 selector는 그
  일부만 얻었다. 상한과 현실 사이의 격차가 논문이 풀 문제다.
- **selector 개선 후보:** (a) 띠 대신 키워드 주변 2차원 창과 차트용 세로 띠, (b) 여러 후보 영역(multi-crop),
  (c) 저해상도 1차 호출(GPT-4o low = 85 토큰)로 위치를 찾은 뒤 고해상도 crop을 보내는 2단계 방식.
- **guard 재설계 후보:** 호출 전 OCR 신호 대신, 모델의 판독 불가 응답을 신호로 원본(또는 넓은 영역)을 재요청하는
  응답 기반 fallback. 프로토콜의 D 정의를 바꾸는 일이므로 사전 등록 전에 사용자가 정한다.
- 두 번째 공급자(Anthropic Haiku 4.5): 실행 코드는 준비됐고 키가 필요하다. Haiku는 28px patch 회계라 1024 resize가 토큰을
  줄일 것으로 예측된다. GPT-4o와 대비되는지 실측할 수 있다.
