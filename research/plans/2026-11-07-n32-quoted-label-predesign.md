## 1. 지금 동작 (main `3e4c972`)

#0 술어는 정규식 넷의 OR이다(영어 #0 `/iu`, F-21 E-3 `/i`, 한국어 둘 `/i`). N-27/N-30 뒤로 넷 모두 라벨 바로 뒤에 별표 0–3개, `\s*`, 구분자 `[:=：]`가 와야 한다. 닫는 따옴표나 괄호가 라벨과 구분자 사이에 끼면 걸리지 않는다.

라벨 13개(N-27 행렬과 같음) × 표기 31개 = 403행을 줄 단독(`<표기> hunter2`)과 문장 안(`Guest wifi <표기> hunter2 is taped …`, `회의실 <표기> hunter2 이니까 …`)에서 보았다. 결과 `matrix`다. 아래 표는 노출된 11라벨 기준이다.

| 표기 | 예 | 문장 안 | 줄 단독 |
|---|---|---|---|
| 큰따옴표 | `"password":`, `"password" :`, `"password"：`, `"password"=` | **semantic** | unknown |
| 작은따옴표 | `'password':` | **semantic** | unknown |
| 괄호 | `(password):`, `(password)：` | **semantic** | unknown |
| 둥근 따옴표 | `“password”:`, `‘password’:` | **semantic** | unknown |
| 전각 괄호·낫표 | `（비밀번호）:`, `「비밀번호」:`, `『비밀번호』:` | **semantic** | unknown |
| JSON 여는 중괄호 | `{"password":` | exact(`code_syntax`) | unknown |
| 강조 + 따옴표 | `**"password"**:` | **semantic** | unknown |

- 노출 라벨은 13개 중 11개다. 나머지 둘은 다음과 같다
  - `API_KEY`는 밑줄 식별자 규칙(`identifier_or_hash`)으로 줄 단독·문장 안 모두 exact다
  - 한국어 `API 키`는 이런 표기에서 문장 안에서도 unknown이라 노출이 아니다
- N-27과 같이 노출은 **문장 안**일 때만 생긴다. 노출된 11라벨의 이 표기들은 줄 단독에서 unknown(압축 금지)이다
- 문장 안 JSON 조각이 `{`로 시작하면 이미 exact다. 구멍은 `"password": "hunter2"`처럼 중괄호 없이 키·값만 붙여 넣은 경우다

## 2. 후보 규칙

모두 라벨 목록, flags, #0 위치를 그대로 두고 **기존 정규식 4개를 제자리에서** 고친다(N-27 L-5와 같다). 새 정규식을 OR로 붙이지 않는다. 정규식 원문은 결과 `candidates`에 있다.

| ID | 라벨과 `\s*` 사이 | 방식 |
|---|---|---|
| U1 | `(?:\*{1,3}\|["'])?` | 닫는 ASCII 따옴표 1개. 여는 쪽은 보지 않는다 |
| U2 | `(?:\*{1,3}\|["')])?` | U1 + 닫는 괄호 |
| U3 | `(?:\*{1,3}\|["')”’）」』])?` | U2 + 둥근 따옴표, 전각 괄호, 낫표 |
| L2 | `(?:\*{1,3}\|"(?<="(L)")\|'(?<='(L)')\|\)(?<=\((L)\)))?` | U2의 닫는 문자를 받되, lookbehind로 라벨 바로 앞의 여는 짝을 확인한다 |
| L3 | L2 + `”(?<=“(L)”)` 등 다섯 쌍 | U3의 닫는 문자에 같은 짝 확인 |
| P2 | 기존 가지 + `"(L)"\|'(L)'\|\((L)\)` | 짝이 맞는 감싸기를 같은 정규식 안의 다른 가지로 둔다 |
| P3 | P2 + `“(L)”`, `‘(L)’`, `（(L)）`, `「(L)」`, `『(L)』` | 〃 |

- U와 L은 왼쪽 경계를 그대로 두고 라벨 뒤 `\*{0,3}` 자리만 바꾼다. 라벨을 먼저 찾는 지금의 탐색 순서도 같다
- P는 기존 가지 옆에 감싸기 가지를 더한다. 감싸기 가지에서는 여는 기호가 왼쪽 경계(`\b`, 한국어 API의 lookbehind)를 대신한다
- `(?:\*{1,3}|X)?`는 X가 없으면 지금의 `\*{0,3}`과 같다. 스크립트가 모든 후보에서 지금 걸리는 입력이 그대로 걸리는지 확인한다
- L은 Codex 교차 검토(§9)가 제안한 형태다. **L과 P는 판정이 같다.** 행렬 403행 × 2배치에서 L2=P2, L3=P3이다. 문장 33개의 술어 결과도 같다
- **L3로 걸리는 입력은 모두 U3로도 걸린다**(행렬·문장에서 L3 양성이면서 U3 음성인 경우 0). L3는 U3에서 여는 짝이 없는 경우만 뺀 것이다
- L은 라벨 목록을 lookbehind 안에 짝마다 한 번씩 되풀이한다. 영어 #0 정규식 원문 길이는 U3 92자, L3 580자다
- 별표와 따옴표를 함께 쓰는 `**"password"**:`는 어느 후보도 잡지 않는다(§7 Q-6)

## 3. 노출과 과보호 (결과 `matrix`, `sentences`)

### 덮는 범위 (문장 안 semantic 11라벨 기준)

| 표기 | U1 | U2 | U3 | L2·P2 | L3·P3 |
|---|---|---|---|---|---|
| `"x":`, `'x':`, `"x" :`, `"x"：`, `"x"=` | 11 | 11 | 11 | 11 | 11 |
| `(x):`, `(x)：` | 0 | 11 | 11 | 11 | 11 |
| `“x”:`, `‘x’:`, `（x）:`, `「x」:`, `『x』:` | 0 | 0 | 11 | 0 | 11 |
| 여는 쪽 없음 `x":` / `x):` | 11 / 0 | 11 / 11 | 11 / 11 | 0 / 0 | 0 / 0 |
| `**"x"**:` | 0 | 0 | 0 | 0 | 0 |

- 손으로 쓴 노출 문장 9개(결과 `sentences.exposure`)
  - 지금 semantic인 것은 7개다. U3·L3·P3는 7개를 모두, U2·L2·P2는 4개, U1은 2개 잡는다
  - 나머지 2개(`'token': 'abc-live-77'`, `{"api_key": …}`)는 다른 규칙으로 이미 exact다
- 걸리면 안 되는 문장 16개(N-27의 9개 + 새 7개)는 모든 후보에서 **#0 술어가 false**다(`predicateHit` 모두 false)
  - 새 7개: `"password manager"`, `"token-based":`, `"passport":`, `"passwords":`, `(token bucket):`, `password's`, `"secret sauce":`
  - 16개 중 5개는 다른 규칙으로 지금도 exact다. 예: `"secret sauce":`는 `code_or_path`, `password_hash:`는 `identifier_or_hash`다. 이 문장들은 "non-exact"가 아니라 "#0 술어 false + 지금 결과 그대로"로 고정해야 한다

### 과보호 (후보가 exact로 만들 문장)

- 모든 후보: 다음 다섯 문장이다
  - `The "token": field in the response …`
  - `Each "secret": entry in the config schema …`
  - `응답의 "토큰": 항목은 …`
  - `Results were "pass": yes and "fail": no …`
  - `Set "token": null when …`
  - API 문서·설정 설명에서 JSON 필드 이름을 따옴표로 부르는 문장이다. N-27 사전 설계 L-4가 걱정한 과보호가 이것이다
  - 결과는 압축하지 않는 쪽(exact)이라 정보는 사라지지 않고 압축 이득만 준다. 영어 #0이 `token:`을, F-21 E-2가 `Pass: the ball …`을 이미 이렇게 보호하는 것과 같은 선택이다
- U2 이상, L2·P2 이상: `We call this the (token): the smallest unit …`
- U만(여는 짝 확인 없음): 다음 두 문장이다. L·P는 둘 다 잡지 않는다
  - `He whispered 'I forgot my password': then …`
  - `Type it again (your password): the form …`
  - 인용·괄호가 라벨 앞에서 시작한 문장이다. 같은 모양이 값과 함께 오면(`(your password): hunter2`) 노출이므로, U의 이 과보호는 그 노출을 막는 대가이기도 하다

| Q-3 | 넣는 방식 | (가) 기존 정규식 4개 제자리 수정 / (나) 새 정규식 OR | **(가)**. N-27 L-5와 같다. 미분 테스트로 "현재 양성 ⊆ 새 양성"을 증명한다 |
| Q-4 | JSON 필드 설명 과보호 | (가) 받아들임 / (나) 피하려고 범위를 줄임 | **(가)**. 정규식으로는 `"token": a single unit`(설명)과 `"token": abc123`(값)을 가를 수 없다. exact는 압축 이득만 잃는다. 저장소 문서에서는 모드 변화가 0이었다. (나)를 고르면 결국 N-32를 고치지 않는 것과 같다 |
| Q-5 | 기존 기대값 이관 | (가) N-27 행렬 78 placement + E-3 원문 1을 새 literal로 이관 / (나) 행렬은 두고 새 행렬 추가 | **(가)**. N-27 행렬이 N-32 미구현 상태를 고정한 것이므로 같은 파일에서 갱신하는 것이 맞다. 과거 기대값은 baseline helper로 보존한다(N-27의 방식) |
| Q-6 | 범위 밖 | `**"x"**:`·`"**x**":` 같은 강조+따옴표 겹침, 대괄호 `[x]:`, 코드 span, 밑줄 강조, `＝`, 복수형 | 넣지 않는다. 겹침은 드물고 정규식 두 단계를 허용하면 역추적이 커진다. 대괄호·코드 span은 이미 unknown이다. 나머지는 N-27 L-3·L-6 그대로다 |

Q-2를 (가)로 권하는 이유:

- **보호 범위.** U3는 L3를 포함한다(§2). U3만 잡는 것은 여는 짝이 라벨 바로 앞에 없는 경우다(`(your password): hunter2`). 이 규칙은 압축을 막는 방향이라, 애매하면 더 많이 잡는 쪽이 안전하다
- **비용.** 술어 단독 값은 U3가 조금 작다(최대 0.80% 대 0.88%). 둘 다 1% 미만이고 차이는 이 측정의 잡음 범위와 비슷하다
- **단순성.** U3는 정규식에 문자 집합 하나를 더한다. L3는 라벨 목록을 짝마다 되풀이해 정규식이 6배 길어진다. 라벨을 고칠 때 아홉 곳을 함께 고쳐야 한다
- **대가.** U3는 §3의 과보호 두 문장(`'… my password':`, `(your password):`)을 더 만든다. 과보호를 줄이는 것을 더 중요하게 보면 (나)를 고른다. 그때 성능 게이트 최악 입력은 같게 두고, 행렬 기대값만 여는 쪽 없는 표기에서 달라진다

   - 과보호 문장(§3)의 결과를 literal로 고정해 한계를 드러낸다
