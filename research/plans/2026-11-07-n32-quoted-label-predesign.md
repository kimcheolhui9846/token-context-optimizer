## 1. 지금 동작 (main `3e4c972`)

#0 술어는 정규식 넷의 OR이다(영어 #0 `/iu`, F-21 E-3 `/i`, 한국어 둘 `/i`). N-27/N-30 뒤로 넷 모두 라벨 바로 뒤에 별표 0–3개, `\s*`, 구분자 `[:=：]`가 와야 한다. 닫는 따옴표나 괄호가 라벨과 구분자 사이에 끼면 걸리지 않는다.

라벨 13개(N-27 행렬과 같음) × 표기 31개 = 403행을 줄 단독(`<표기> hunter2`)과 문장 안(`Guest wifi <표기> hunter2 is taped …`, `회의실 <표기> hunter2 이니까 …`)에서 보았다. 결과 `matrix`다.

| 표기 | 예 | 문장 안 | 줄 단독 |
|---|---|---|---|
| 큰따옴표 | `"password":`, `"password" :`, `"password"：`, `"password"=` | **semantic** | unknown |
| 작은따옴표 | `'password':` | **semantic** | unknown |
| 괄호 | `(password):`, `(password)：` | **semantic** | unknown |
| 둥근 따옴표 | `“password”:`, `‘password’:` | **semantic** | unknown |
| 전각 괄호·낫표 | `（비밀번호）:`, `「비밀번호」:`, `『비밀번호』:` | **semantic** | unknown |
| JSON 여는 중괄호 | `{"password":` | exact(`code_syntax`) | unknown |
| 강조 + 따옴표 | `**"password"**:` | **semantic** | unknown |

- 노출 라벨은 13개 중 11개다. `API_KEY`는 밑줄 식별자 규칙(`identifier_or_hash`)으로 어디서나 exact다. 한국어 `API 키`는 이런 표기에서 문장 안에서도 unknown이라 노출이 아니다
- N-27과 같이 노출은 **문장 안**일 때만 생긴다. 줄 단독은 모두 unknown(압축 금지)이다
- 문장 안 JSON 조각이 `{`로 시작하면 이미 exact다. 구멍은 `"password": "hunter2"`처럼 중괄호 없이 키·값만 붙여 넣은 경우다

## 2. 후보 규칙

모두 라벨 목록, flags, #0 위치를 그대로 두고 **기존 정규식 4개를 제자리에서** 고친다(N-27 L-5와 같다). 새 정규식을 OR로 붙이지 않는다. U1–U3는 왼쪽 경계도 그대로 두고 라벨 뒤 `\*{0,3}` 자리만 바꾼다. P2·P3는 기존 가지를 그대로 둔 채 짝이 맞는 감싸기 가지를 같은 정규식 안에 더한다. 감싸기 가지에서는 여는 기호가 왼쪽 경계(`\b`, 한국어 API의 lookbehind)를 대신한다. 정규식 원문은 결과 `candidates`에 있다.

| ID | 라벨과 `\s*` 사이 | 방식 |
|---|---|---|
| U1 | `(?:\*{1,3}\|["'])?` | 닫는 ASCII 따옴표 1개. 여는 쪽은 보지 않는다 |
| U2 | `(?:\*{1,3}\|["')])?` | U1 + 닫는 괄호 |
| U3 | `(?:\*{1,3}\|["')”’）」』])?` | U2 + 둥근 따옴표, 전각 괄호, 낫표 |
| P2 | 기존 가지 + `"(L)"\|'(L)'\|\((L)\)` | 짝이 맞는 감싸기를 같은 정규식 안의 다른 가지로 둔다 |
| P3 | P2 + `“(L)”`, `‘(L)’`, `（(L)）`, `「(L)」`, `『(L)』` | 〃 |

- `(?:\*{1,3}|X)?`는 X가 없으면 지금의 `\*{0,3}`과 같다. 스크립트가 모든 후보에서 지금 걸리는 입력이 그대로 걸리는지 확인한다
- U는 짝을 보지 않는다. `password":`처럼 여는 따옴표가 없어도 걸린다. P는 짝이 맞아야 걸린다
- 별표와 따옴표를 함께 쓰는 `**"password"**:`는 어느 후보도 잡지 않는다(§7 Q-6)

## 3. 노출과 과보호 (결과 `matrix`, `sentences`)

### 덮는 범위 (문장 안 semantic 11라벨 기준)

| 표기 | U1 | U2 | U3 | P2 | P3 |
|---|---|---|---|---|---|
| `"x":`, `'x':`, `"x" :`, `"x"：`, `"x"=` | 11 | 11 | 11 | 11 | 11 |
| `(x):`, `(x)：` | 0 | 11 | 11 | 11 | 11 |
| `“x”:`, `‘x’:`, `（x）:`, `「x」:`, `『x』:` | 0 | 0 | 11 | 0 | 11 |
| 여는 쪽 없음 `x":`, `x):` | 11 / 0 | 11 | 11 | 0 | 0 |
| `**"x"**:` | 0 | 0 | 0 | 0 | 0 |

- 손으로 쓴 노출 문장 9개(결과 `sentences.exposure`) 중 지금 semantic인 7개를 U3·P3는 모두, U2·P2는 4개, U1은 2개 잡는다. 나머지 2개(`'token': 'abc-live-77'`, `{"api_key": …}`)는 다른 규칙으로 이미 exact다
- 걸리면 안 되는 문장 16개(N-27의 9개 + 새 7개)는 모든 후보 술어에서 걸리지 않는다(`predicateHit` 모두 false)
  - 새 7개: `"password manager"`, `"token-based":`, `"passport":`, `"passwords":`, `(token bucket):`, `password's`, `"secret sauce":`

### 과보호 (후보가 exact로 만들 문장)

- 모든 후보: `The "token": field in the response …`, `Each "secret": entry in the config schema …`, `응답의 "토큰": 항목은 …`, `Results were "pass": yes and "fail": no …`, `Set "token": null when …`
  - API 문서·설정 설명에서 JSON 필드 이름을 따옴표로 부르는 문장이다. N-27 사전 설계 L-4가 걱정한 과보호가 이것이다
  - 결과는 압축하지 않는 쪽(exact)이라 정보는 사라지지 않고 압축 이득만 준다. 영어 #0이 `token:`을, F-21 E-2가 `Pass: the ball …`을 이미 이렇게 보호하는 것과 같은 선택이다
- U2 이상: `We call this the (token): the smallest unit …`
- U만(짝 검사 없음): `He whispered 'I forgot my password': then …`, `Type it again (your password): the form …`. 인용·괄호가 라벨 앞에서 시작한 문장이다. P는 이 둘을 잡지 않는다

## 8. 구현 PR에 넘길 조건 (Codex)

1. 계획 PR을 먼저 낸다. Q-1–Q-6 결정, 영향 조사(기존 입력 전체에서 모드와 `reasons`가 바뀌는 행 수, 계획·핸드오프 출처는 따로 셈), 기대값 이관 목록, 성능 게이트 사전등록을 담는다
2. 테스트

   - 음성: §3의 16개 문장
   - 미분 테스트: N-27이 승인한 정규식 4개를 literal로 고정하고 "현재 양성 ⊆ 새 양성"을 검사한다. 새 양성은 Q-1 표기뿐임을 행렬로 확인한다
   - 과보호 문장(§3)의 결과를 literal로 고정해 한계를 드러낸다
3. 성능 게이트: N-27 도구 복사본을 쓴다. 3%, A′/A [0.97, 1.03], 6블록·36라운드, warmup 12, seed, 10,000회 block bootstrap, 경계 통과 규칙, INVALID-only 1회 재시도는 그대로 둔다
   - 최악 입력(§6에서 증가가 큰 것): `"password"` + NBSP×60, `"password"` + NBSP×8, `"password"` + U+3000×8, `"password" ` 반복, `(password) ` 반복, `"비밀번호"` + NBSP×8, `「비밀번호」` + NBSP×8, `"api키"` + NBSP×8
   - N-27 20 recipe도 다시 넣는다. 같은 정규식 4개를 다시 고치기 때문이다
