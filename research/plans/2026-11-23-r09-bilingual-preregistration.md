- 작성 2026-11-23. Tier E. 기준 main `7c9f4370387ca435efd49167785dc6240e27e1ee`.
- 사용자 승인 범위: 합성 자료 24쌍, 로컬 실측, Draft PR까지. 실험 API 비용 0원.
- 이전 8쪽 심사본의 R09 비선택 결정과는 별개인 후속 연구다. 원고, 패키지, 제품, 기존 실험 결과는 바꾸지 않는다. D04는 계속 사용자 보류다.
- 이 문서와 `research/results/r09-bilingual/heldout/freeze-manifest.json`이 들어간 커밋이 등록 커밋이다. 그 커밋 전에 본시험 48장에 선택기를 적용하지 않았다.

## 1. 질문

같은 내용을 영어와 한국어로 제시했을 때, 기존 단일 질의 선택기(`research/src/selector.mjs`의 `createOcr`, `selectWindow`)가 페이지 전체로 되돌아가지 않고 질문에 필요한 근거를 잘라낼 수 있는가?

기존 선택기는 영어 OCR(`eng.traineddata`)을 쓰고, 질문을 ASCII 토큰(`[a-z0-9-]`)으로 자른다. 따라서 한국어 질문의 한글 낱말은 키가 되지 않는다. 이 설계 특성을 미리 밝혀 두고 언어별 차이를 관측한다. 측정 대상은 **기하적 포함**이다. 모델 정확도, 청구 토큰, 추론 비용 감소, 실제 업무 문서 전반에 대한 결론은 범위 밖이다.

## 2. 자료

### 2.1 구성

- 문서형 3(일정표 `schedule`, 거래명세서 `invoice`, 상태표 `status`) × 레이아웃 2(`table`, `cards`) × 앵커 조건 2(`code`, `nl`) × seed 2 = 24쌍, 48장
- 각 쌍은 영어(`en`)와 한국어(`ko`) 페이지 하나씩이다. 한 쌍의 두 페이지는 다음이 같다.
  - 문답 의미
  - 답 값: ASCII, 자릿수와 구분자까지 같다
  - 지면 규격: 1280×960
  - 칸 좌표, 대상 행 위치, 방해 행과 그 순서
- 언어별로 다른 것은 제목, 열 머리, 자연어 표지, 기타 필드(장소·공급처·상태)의 문구뿐이다.
- 각 페이지는 8행(표) 또는 8장(카드)이다. 행마다 코드, 표지, 답 필드, 기타 필드가 있다.

### 2.2 앵커 조건

- `code`(주 비교, 12쌍): 양 언어의 질문과 페이지에 같은 업무용 영숫자 코드(`SX-`, `KT-`, `PX-` + 4자리)가 나온다.
  - 질문의 실제 매칭 토큰은 양 언어 모두 지정 코드 **하나**다. 영어 질문은 고정 불용어와 3자 미만 낱말로만 짠다. 예: `When is SX-5134?`, `How much is KT-9600?`, `What number is shown for PX-2149?`
  - 코드는 대상 행에 정확히 한 번 나온다. 다른 행은 같은 길이의 다른 코드를 쓴다. 따라서 접두 일치 규칙으로 같은 행이 되는 혼입이 없다.
- `nl`(구조적 대조, 12쌍): 질문이 언어별 자연어 표지(예: `budget review` / `예산 검토`)를 가리킨다.
  - 한국어 질문은 매칭 가능한 ASCII 토큰이 0개다. 따라서 이 조건에서 한국어 쪽의 저조한 매칭(불일치 → 전체 프레임)은 **설계상 예상되는 동작**이다.
  - 영어 질문의 키는 대상 행 표지의 낱말뿐이다.
- 48개 질문의 키와 원문 기준 예상 표지는 `heldout/token-manifest.json`에 고정했다. 이 키는 `selectWindow`와 같은 `keywords()` 규칙에서 `off`/`yes`를 뺀 것이다. 원문 기준 일치 여부는 항목마다 합성 OCR 줄 하나를 만들어 `selectWindow` 자체로 판정했다.
  - 코드 24문항: 키 = [코드], 원문 일치 = 코드 칸 하나
  - 영어 자연어 12문항: 원문 일치 = 대상 표지 칸 하나
  - 한국어 자연어 12문항: 키 0개
- 질문에는 정답 값이나 그 숫자열 일부가 들어가지 않는다. 생성기는 숫자만 뽑은 값과 코드가 서로를 포함하면 다시 뽑는다.

### 2.3 seed와 위치 배정

- seed는 코드, 답 값, 표지 선택, 방해 행 순서, 기타 필드 값을 바꾼다. 난수는 문자열 시드(`r09-design-1|heldout|문서형|레이아웃|앵커|seed`)에서 시작하는 FNV-1a + mulberry32다.
- 대상 위치는 다음 배정표로 미리 고정했다. 문서형과 무관하다. 표는 행 번호, 카드는 왼쪽→오른쪽, 위→아래 순서의 카드 번호이며 0부터 센다.

| 레이아웃 | code s1 | code s2 | nl s1 | nl s2 |
|---|---|---|---|---|
| table | 2 | 5 | 5 | 2 |
| cards | 3 | 6 | 6 | 3 |

### 2.4 렌더링과 금표준

- 글꼴: 설치된 Noto Sans KR 가변 글꼴 `NotoSansKR-VF.ttf` 하나를 양 언어에 쓴다.
  - SHA-256 `018174e8cdd366aff67c8d366c7dc806a7babbe7f2819fc23b00d59f7b8353d0`, `Version 2.04;241114210130;non-release`, SIL OFL 1.1
  - 굵기 축 400, 본문 24px, 제목 32px
  - 렌더러는 Pillow 12.3.0 + FreeType 2.14.3 BASIC 레이아웃(raqm 없음)이다.
  - `render.py`는 글꼴 파일을 해시한 뒤 **그 바이트로** 글꼴을 연다. 해시가 등록값과 다르면 중단한다. 글꼴 파일은 저장소에 넣지 않는다.
- 같은 위치란 같은 칸과 같은 기준점(칸 왼쪽 +12px, 칸 세로 중앙, `lm` 앵커)을 뜻한다. 실제 잉크 폭은 언어마다 다를 수 있다. 각 항목의 실제 잉크 사각형은 `render.json`에, 금표준 부분의 폭·높이는 `gold.json`에 보관한다.
- 금표준은 질문에 답하는 데 필요한 사전 지정 잉크다. 두 부분으로 이뤄진다.
  - 앵커: `code` 조건은 코드 칸, `nl` 조건은 표지 칸
  - 대상 행의 답 값 칸
  - 각 부분은 그 항목만 따로 그린 층에서 0이 아닌 픽셀의 경계 상자이며, 반개방 정수 좌표다.
- 렌더 검사(`render-check.json`). 48장 모두 문제 0이다.
  - 모든 잉크가 지정 칸 안에 있다(잘림 없음)
  - 잉크 상자끼리, 그리고 잉크와 구분선이 겹치지 않는다
  - 칸끼리 겹치지 않는다
  - 모든 글자가 글꼴 cmap에 있다(대체 문자 없음)
- 작성자 눈 비교용 한영 대표쌍(금표준 빨간 테두리)은 `heldout/review/`에 둔다. 선택기 입력이 아니다.

## 3. 선택기 입력과 실행

- 선택기에는 원본 PNG 픽셀과 질문만 들어간다. `r09-run.mjs`는 `questions.json`(id, file, question)과 이미지만 읽는다. 답, 코드, 금표준, 설계 파일은 읽지 않는다.
- `createOcr()`는 고정된 영어 OCR이다. 긴 변을 4096px까지(최대 4배) 키우고, 좌표는 원본 픽셀로 되돌린다. 그다음 `selectWindow(lines, question, width, height)`를 수정 없이 쓴다.
  - 일치하면 그 창(선택기 자체 패딩 포함)을 원본 픽셀 좌표로 평가한다.
  - 불일치하면 기존 실험 2의 C 경로대로 전체 프레임을 쓴다.
  - 신뢰도 가드(D 경로)는 적용하지 않는다(실험 2의 C와 같다).
- 고정 사항
  - Node 단일 프로세스, tesseract 작업자 1개(CPU), 질문 파일 순서
  - 선택기 Git blob `b3b4965b2d330907c0143fe178013aace1be8372`
  - `research/package-lock.json` blob `6b103b97c99527975958a7cb0fd023e0dc134cf0`(sharp 0.35.4, tesseract.js 5.1.1)
  - `eng.traineddata` SHA-256 `5dc5d8d640a212c9d6184921ba103b186f50e0fed9ee716c53e6b312b400d747`. R02 immutable 연구 사본에서 읽기 전용으로 복사했다.
- 오프라인 실행
  - D03의 `tools/d03/guard/node-netguard.cjs`를 `NODE_OPTIONS=--require`로 주입한다. 이 가드는 fetch, TCP/TLS/HTTP, UDP, DNS를 막고 기록한다.
  - 연구 키 환경변수는 지운다. 모델 서버, 외부 OCR, 유료 호출은 0이다.
  - 의존성 준비(`npm ci --ignore-scripts`, OCR 자료 복사)는 본 측정과 분리한다.

  - 정상적인 불일치(no-match)는 선택기의 결과이지 오류가 아니다.
- 원시 기록에는 다음을 보존한다. 영어 OCR이 한글을 오독한 경우도 그대로 측정에 포함한다.
  - 키
  - 모든 OCR 줄과 단어 좌표
  - 점수가 0보다 큰 후보 줄의 점수와 신뢰도, 동률 수
  - 선택된 줄
  - 창

## 4. 판정 규칙

- 좌표는 원본 픽셀의 반개방 사각형 [왼쪽, 오른쪽) × [위, 아래)이다. 실수 좌표를 정수로 바꿀 때는 바깥쪽으로 반올림한다(좌상단 floor, 우하단 ceil). 이번 금표준은 이미 정수다. 창의 기존 패딩 이후 좌표를 쓰며, 허용 오차는 0px이다.
- 이미지마다 다음 다섯 범주 중 하나로 판정한다.
  1. `window_complete`(**주 성공**): 일치했고, 창 넓이가 0보다 크고 페이지 넓이보다 엄격히 작으며, 금표준의 모든 부분(모든 변)이 창 안에 있다
  2. `window_partial`: 작은 창이지만 금표준 일부가 빠졌다
  3. `matched_full`: 일치했지만 패딩 후 창이 페이지 전체다
  4. `no_match_full`: 불일치해서 전체 프레임을 반환했다
  5. `tech_error`: 기술 오류
- 최종 근거 보존은 실제로 넘겨지는 영역(창 또는 전체 프레임)이 금표준을 모두 담는지로 본다. 1·3·4는 보존, 2는 미보존, 5는 미관측이다.
- 면적비는 창 넓이 ÷ 페이지 넓이다. 전체 프레임은 1이다.
- 언어 차이는 KO−EN으로 고정한다: (KO만 성공한 쌍 수 − EN만 성공한 쌍 수) ÷ 해당 집합의 쌍 수.
  - 주 효과: `code` 12쌍(분모 12)
  - 대조 조건: `nl` 12쌍(분모 12)
  - 부차 결과: 전체 24쌍(분모 24). 균등 배분한 이 문서 집합에 대한 결과일 뿐이다.
- 집합마다 다음을 함께 보고한다.
  - 양언어 성공/실패의 2×2 표, 불일치 양방향 수
  - 언어별 범주 원시값
  - 문서형 × 앵커 × 언어 계층별 수와 분모
- 기술 결측
  - 결측 언어는 해당 집합의 고정 분모에서 운영상 실패로 세고, 기술 결측으로 따로 표시한다.
  - 완전 쌍만의 표와 분모도 낸다.
  - 상·하한은 미관측 성공을 0/1로 두고 고정 분모로 계산한다. 하한은 KO 결측=0·EN 결측=1, 상한은 그 반대다. 동시 결측도 같은 방식으로 처리한다.
- 사전에 정한 유한 합성 사례군이고 레이아웃을 공유하므로 p값과 모집단 신뢰구간은 계산하지 않는다. 외부 모집단이나 언어 자체에 대한 인과 효과도 추론하지 않는다.

## 5. 재현성과 확정 절차

- 같은 장비, 같은 파일, 같은 코드로 두 번 실행한다. 출력 경로는 `run-a`, `run-b`로 따로 둔다.
- `raw.jsonl`과 `score.json`, `summary.md`가 두 실행에서 **바이트 일치**해야 한다. 시각, 소요 시간, 경로 같은 비결정적 메타데이터는 `run-meta.json`에 따로 둔다.
- 바이트가 다르면 미리 정한 정규화 해시와 비교한다. 정규화는 모든 실수를 소수 셋째 자리로 반올림한 뒤의 JSON SHA-256이다. 그래도 다르면 결과 확정을 중단하고 원인을 기록한다.
- 입력 이미지와 매니페스트는 렌더를 두 번 해서 바이트 일치를 확인했다(48장 + JSON 6개).
- 동결 매니페스트의 입력 해시는 생성기가 쓴 LF 바이트 기준이다. 이는 커밋 blob과 같다. autocrlf로 CRLF가 된 작업 사본에서는 JSON 해시가 다르게 나오므로, 그때는 다시 생성한 사본이나 blob으로 대조한다. 코드 해시는 `git hash-object`(blob) 기준이다.
- 측정 직전에 `r09-freeze.mjs --check`로 입력과 코드 해시를 동결 매니페스트와 대조한다. 하나라도 다르면 실행하지 않는다.
- 합계는 독립 도구(`tools/r09/recount.py`, Python)로 원시 기록에서 다시 계산해 Node 채점기와 대조한다. 그 결과는 새 출력 경로에 쓴다.
- 결과를 보고 질문, 자료, 규칙을 바꾸지 않는다. 동결 자료가 사전등록 검사에 실패하면 결함으로 기록하고 멈춘다.

## 6. 개발용 fixture와 동결 전 이력

- 배선과 채점기 확인은 별도 fixture(`dev`)에서만 했다. 장비 대여 목록이라는 다른 문서형, 한 열 목록이라는 다른 레이아웃, 1100×800이라는 다른 지면을 쓴 2쌍 4장이다.
- 본시험 템플릿(문서형 3종, 레이아웃 2종, 칸 좌표, 배정표)은 dev 실행 **전에** 작성했다. dev 결과를 보고 바꾸지 않았다.
- 동결 전 본시험 설계는 두 번 고쳤다. 두 번 모두 본시험 48장에 선택기를 적용하기 전이며, 정답·선택 결과와 무관한 결함 수정이다.
  1. 설계 검사가 공급처 `Mirae Office`와 표지 `Office chair`의 키 충돌을 잡았다. 공급처를 `Mirae Stationery`/`미래문구`로 바꿨다.
  2. 작성자 시각 비교에서 일정표 열 머리 순서가 값 배치와 뒤바뀐 것을 발견했다(`Time`, `Venue` 머리 아래에 각각 장소와 시간이 들어감). 열 머리를 `Code, Session, Venue, Time`으로 바로잡았다.

## 6a. 수정 1: 물리 변환 재생 검증 (측정 전, PM 요청)
