# strict 성능 게이트 잡음 분석 (2026-11-02)

- 작성: Claude Code, 2026-11-02. 기준 main `8a149b0`
- 목적: 6.12c에서 쓴 strict 성능 게이트("같은 프로세스 교대 9회 + A/A 대조, B/A ≤ 1.03, A′/A가 [0.97, 1.03] 밖이면 무효")가 측정 잡음을 얼마나 견디는지 원자료로 확인한다. 다음 성능 게이트가 있는 Task의 계획에 쓸 권장안을 정한다
- 범위: 새로 측정하지 않는다. 이미 커밋된 원자료만 다시 계산한다. 제품 코드와 측정 스크립트는 바꾸지 않는다
- 재현: `node research/src/perf-gate-noise.mjs --out research/results/perf-gate-noise/2026-11-02.json` (bootstrap seed 고정, 같은 입력이면 같은 출력)

## 1. 자료

- `docs/research/evidence/wbs-6.12c/`의 세 실행: `measurement-attempt2.json`, `-scancap.json`, `-scancap-r2.json`
- 연산 셋(jpegIndex, jpegCrop, pngIndex)마다 warmup 3회 뒤 9라운드를 돌렸다. 한 라운드 안에서는 **항상 A → A′ → B 순서**다(`scripts/measure-jpeg-tolerant.mjs:424-425`). 증거의 `order` 필드에는 위치가 아니라 변형 이름이 들어 있다
- A와 A′는 같은 소스·같은 빌드(6e6b016)의 독립 사본이다. 그래서 A′/A는 순수한 잡음과 위치 효과만 보여 준다. B는 그때그때의 변경 소스다. 세 실행 모두 strict 코드는 같다(strict 접두부 불변 확인)

## 2. 결과

### 2.1 추정량 비교: 중앙값 비율 vs 짝지은 비율

- 중앙값 비율: median(B) / median(A). 6.12c 게이트가 쓴 방식이다
- 짝지은 비율: 라운드마다 B_i / A_i를 구하고 그 중앙값을 쓴다. 같은 라운드는 기계 상태가 비슷하다는 점을 이용한다

| 연산 | 비교 | 중앙값 비율 (세 실행) | 폭 | 짝지은 비율 (세 실행) | 폭 |
|---|---|---|---|---|---|
| jpegIndex | A′/A | 1.0159, 0.9883, 0.9703 | 0.046 | 0.9784, 0.9798, 0.9769 | **0.003** |
| jpegIndex | B/A | 1.0116, 0.9362, 0.9795 | 0.075 | 0.9801, 0.9748, 0.9785 | **0.005** |
| jpegCrop | A′/A | 0.9991, 1.0010, 1.0200 | 0.021 | 1.0109, 0.9986, 1.0245 | 0.026 |
| jpegCrop | B/A | 0.9953, 1.0046, 0.9958 | 0.009 | 0.9896, 1.0102, 1.0037 | 0.021 |
| pngIndex | A′/A | 0.9997, 1.0034, 0.9944 | 0.009 | 0.9972, 1.0019, 0.9982 | 0.005 |
| pngIndex | B/A | 0.9913, 0.9942, 0.9970 | 0.006 | 0.9872, 0.9981, 0.9927 | 0.011 |

- **jpegIndex는 짝지은 비율이 실행 간 폭을 약 15배 줄인다**(0.075 → 0.005). 원자료를 보면 이 연산은 한 실행 안에서 약 157 ms 구간과 약 148 ms 구간으로 나뉜다. 구간이 바뀌는 라운드가 변형마다 하나씩 어긋나서, 9개 중앙값이 어느 구간에 떨어지느냐에 따라 비율이 뒤집힌다. scancap 실행의 B/A 0.9362가 그 예다
- jpegCrop과 pngIndex는 이런 두 구간이 없다. 두 추정량의 폭이 비슷하거나 짝지은 쪽이 조금 넓다

### 2.2 위치 효과 의심: jpegIndex에서 맨 앞 A가 약 2% 느리다

- jpegIndex의 짝지은 A′/A가 세 실행 모두 0.977–0.980이다. A와 A′는 같은 코드인데 A가 꾸준히 약 2% 느리다. 실행 2와 3에서는 bootstrap 95% 구간이 1을 포함하지 않는다(0.967–0.994, 0.946–0.985)
- 짝지은 B/A(0.975–0.980)도 A′/A와 거의 같다. 즉 B와 A′는 차이가 없고, A만 느리다
- 해석 두 가지를 지금 자료로는 가를 수 없다
  - (가) 위치 효과: 라운드의 첫 실행이 손해를 본다(캐시, GC, 타이머 등)
  - (나) 사본 효과: A 모듈 사본 자체가 느리다(메모리 배치 등). A·A′·B는 서로 다른 모듈 사본이다
- 어느 쪽이든 결과는 같다. **B/A가 jpegIndex에서 약 2% 유리하게 나온다.** 그래서 게이트가 B의 2~3% 회귀를 놓칠 수 있다. 6.12c의 strict 코드는 바뀌지 않았으므로 이번 결론이 틀린 것은 아니다. 다만 다음에 strict 경로를 실제로 바꾸는 Task에서는 문제가 된다
- jpegCrop(0.999–1.025)과 pngIndex(0.997–1.002)에는 같은 방향의 꾸준한 치우침이 없다

### 2.3 실행 안의 흐름(drift)

- 뒤 4라운드(5–8) 평균 / 앞 5라운드(0–4) 평균이 jpegIndex에서 0.936–0.988이다. 뒤로 갈수록 약 1–6% 빨라진다(A·A′만 보면 3–6%). warmup 3회로는 이 연산이 안정되지 않는다
- 다른 두 연산은 0.979–1.031이고 방향이 일정하지 않다

### 2.4 게이트를 넘을 확률 (bootstrap)

- strict 코드가 같은데도 재표본의 B/A가 1.03을 넘는 비율을 셌다. 실행 3개 × 연산 3개, 모두 9칸이다. jpegCrop 실행 1(짝지은 14%, 중앙값 6%)과 jpegIndex 실행 3(두 추정량 모두 14%)의 두 칸에서 컸고, 나머지 7칸은 1% 미만이었다
- 즉 9라운드와 3% 허용폭으로는 실제 회귀가 없어도 일부 실행에서 판정이 경계에 걸릴 수 있다. 세 실행이 모두 통과한 것은 이와 모순되지 않는다. 다만 표본이 작아서 이 비율을 일반적인 오판정 확률로 읽으면 안 된다

### 2.5 기준선 선택: A만, A′만, A·A′ 평균

같은 짝지은 방식에서 B를 무엇과 비교할지에 따라 결과가 달라진다.

| 연산 | B / A | B / A′ | B / mean(A, A′) |
|---|---|---|---|
| jpegIndex | 0.9801, 0.9748, 0.9785 (폭 0.005) | 0.9968, 0.9982, 1.0140 (폭 0.017) | 0.9852, 0.9907, 0.9953 (폭 0.010) |
| jpegCrop | 0.9896, 1.0102, 1.0037 (폭 0.021) | 0.9963, 1.0139, 0.9809 (폭 0.033) | 1.0036, 1.0061, 0.9928 (폭 0.013) |
| pngIndex | 0.9872, 0.9981, 0.9927 (폭 0.011) | 0.9922, 0.9943, 0.9992 (폭 0.007) | 0.9905, 0.9898, 0.9954 (폭 0.006) |

- B/A가 jpegIndex에서 가장 좁은 것은 A가 꾸준히 느려서 치우침이 안정적이기 때문이다. 폭은 좁지만 2% 유리하게 치우친 값이다
- B/A′는 치우침이 없는 대신 흔들린다. jpegIndex 실행 3에서 재표본의 36%가 1.03을 넘었다(실제 값 1.014)
- A·A′ 평균은 세 연산 모두 폭이 1.3% 이하이고, jpegIndex의 치우침은 약 절반(약 1%)만 남는다. 같은 칸의 1.03 초과 비율은 15%다
- 이 비교는 순서가 고정된 지금 자료에서 나온 것이다. 순서를 돌리면(G-1) 세 기준선의 차이가 줄어들 것으로 보지만, 확인은 측정이 필요하다

## 3. 권장안 (다음 성능 게이트 계획에 적용)

| ID | 권장 | 이유 |
|---|---|---|
| G-1 | 라운드 안 순서를 돌린다. ABC, BCA, CAB를 차례로 쓰고, 라운드 수는 3의 배수(예: 18)로 한다 | 2.2의 위치 효과를 상쇄한다. 동시에 (가)·(나)를 가르는 실험이 된다. 돌린 뒤에도 A′/A가 0.98이면 (나)다 |
| G-2 | 판정 추정량은 짝지은 비율의 중앙값으로 한다. 기준선은 라운드마다 A와 A′의 평균으로 둔다(B_i / mean(A_i, A′_i)) | 2.1에서 두 구간 연산의 실행 간 폭이 크게 준다. 2.5에서 A·A′ 평균 기준선이 세 연산 모두 폭 1.3% 이하로 가장 고르고, 사본 하나의 치우침을 절반으로 줄인다 |
| G-3 | A/A 대조도 짝지은 A′/A로 판정한다. [0.97, 1.03] 밖이면 무효인 규칙은 유지한다 | 같은 추정량을 써야 무효 판정과 통과 판정이 일관된다 |
| G-4 | warmup을 늘린다(예: 9회). 측정 뒤 앞쪽/뒤쪽 평균 비를 증거에 기록한다 | 2.3의 흐름. 기록이 있으면 흐름이 컸던 실행을 사후에 알아볼 수 있다 |
| G-5 | bootstrap 95% 구간을 증거에 함께 남긴다. 판정은 점추정으로 하되, 구간 상한이 1.03을 넘으면 "경계 통과"로 표시한다. 이 표시 기준은 측정 전에 계획에 적는다 | 2.4. 경계 결과를 숨기지도, 사후에 기준을 바꾸지도 않는다 |
| G-6 | 원자료(라운드·위치·시간·출력 hash)를 지금처럼 모두 남긴다. 위치 필드는 변형 이름이 아니라 실제 순번을 기록한다 | 이번 분석은 원자료가 있어서 가능했다. 위치를 명시하면 G-1의 효과를 바로 검증할 수 있다 |

- 허용폭 3%는 그대로 둔다. G-2 추정량의 실행 간 폭은 세 연산 모두 1.3% 이하다(2.5)
- 남은 치우침은 원인에 따라 다르게 다룬다. (가) 위치 효과라면 G-1로 사라진다. (나) 사본 효과라면 G-1 뒤에도 A′/A가 약 0.98로 남는다. 그때는 A 사본 구성(빌드·로드 방식)을 다시 보고, 그 전까지는 G-2의 평균 기준선이 치우침을 절반으로 줄인 상태로 판정한다
- 이 권장안은 계획 단계에서 정하는 규칙이다. 이미 끝난 6.12c 판정은 다시 하지 않는다

## 4. 한계

- 실행 세 번, 기계 한 대(Windows), 같은 날 연속 측정이다. 다른 날·다른 부하에서의 폭은 모른다
- 위치 효과는 jpegIndex 한 연산에서만 보였다. 원인을 가르려면 G-1처럼 순서를 돌린 측정이 필요하다. 이 문서는 새로 측정하지 않는다
- bootstrap은 9개 표본을 재표본한다. 표본이 작아 구간 자체가 거칠다
- F-21(PR #61·#63) 성능 증거는 라운드별 원자료와 순서가 남아 있지 않아 이 분석에 넣지 못했다
