### D-4 (N-14)

**사실 (main `7709837`, `@modelcontextprotocol/server` 2.0.0)**

- 서버는 SDK의 `serveStdio`를 쓴다(`src/server/index.ts:3,248`, main `59c33c9`에서는 `:3,254`)
- SDK `ReadBuffer`는 들어오는 버퍼가 `STDIO_DEFAULT_MAX_BUFFER_SIZE = 10 * 1024 * 1024`를 넘으면 버퍼를 비우고 예외를 던진다(`node_modules/@modelcontextprotocol/server/dist/src-CX2iR2pK.mjs:7067-7078`). 요청 id를 읽기 전이라 JSON-RPC 오류 응답을 보낼 수 없다
  - Codex(2026-10-28)가 실제 `ReadBuffer.append`로 확인했다: 10 MiB는 통과, 1바이트 넘으면 버퍼 초기화와 예외. JSON 파싱·id 해석보다 먼저다
  - 그 뒤 클라이언트가 겪는 일은 정해져 있지 않다. Codex의 실제 transport 재현에서는 오류 뒤 연결이 닫혔다(error → close). 아래 n01 관측에서는 20초 동안 응답이 없었다. 문안은 둘 중 하나로 단정하지 않는다
- 상한은 `text` 값이 아니라 **JSON-RPC 한 줄 전체**에 걸린다. JSON 이스케이프(`"`, `\`, 줄바꿈, 제어 문자)가 있으면 같은 글자 수라도 줄이 길어진다
- 관측(`docs/research/evidence/n01/mcp-large-2026-10-23T15-40-49.857Z.json`, Node v24.18.0)
  - `classify_context`에 10,485,760바이트 text → JSON-RPC 10,485,868바이트 → 20초 동안 응답 없음
  - 20,971,520바이트 → `stdin: write EOF`(214 ms)
- 해당 도구: 문자열 본문을 받는 `estimate_context`·`classify_context`. 파일은 경로로 넘기므로 `index_artifact`·`index_image_artifact`는 이 상한과 관계없다. 응답 쪽(서버 → 클라이언트) 상한은 클라이언트 구현에 달려 있어 이 메모에서 다루지 않는다

**문안 (가)·(ㄱ)+(ㄴ)**

- README "Tool Behavior" 끝에 한 문단:

> `estimate_context` and `classify_context` receive text inline over the STDIO
> transport. The MCP SDK read buffer (`@modelcontextprotocol/server` 2.0.0) is
> 10 MiB (10,485,760 bytes) for one JSON-RPC message, including JSON escaping.
> A larger request is discarded before its id is read, so no JSON-RPC error
> response is returned; the connection may close, and what the client reports
> depends on the client. For larger text, write it to a file under an allowed
> root and use `index_artifact` and `query_artifact`. That path has its own
> 10 MiB (10,485,760 bytes) file limit and returns `too_large` above it; split
> larger text into several files.

- `docs/design.md` "v1 Boundaries"의 Excluded 목록에 한 줄:

> - Inline text requests larger than the 10 MiB STDIO message limit (see README "Tool Behavior").

- 주의: `index_artifact`도 파일 상한이 10 MiB다(`src/core/artifacts.ts:36`, main `59c33c9`에서는 `:37`, 검사는 `read-bounded-file.ts`의 `too_large`). 두 상한이 같은 값이지만 다른 것이므로, 문안에서 둘을 하나로 묶지 않는다. 다만 파일로 옮기라는 대안 바로 뒤에 파일 상한을 따로 적는다. 없으면 10 MiB를 넘는 텍스트에 막힌 길을 안내하게 된다(Codex 확인: 10,485,761바이트 파일 → `too_large`)
- 문안의 `too_large`와 "split" 안내는 6.10 구현 때 `artifacts.ts`의 실제 오류 코드와 README의 기존 `index_artifact` 설명에 맞춰 다시 확인한다

### D-5 (N-25)

- 사실: 4:4:4에서 `B ≈ W*H/64`이므로 회계값은 약 `21*W*H`다. `21*W*H ≤ 134,217,728`에서 `W*H ≤ 약 6,391,320`(약 6.39 MP)이다
- 경계 예: 3088×2064(6,373,632 px)는 회계값 약 133.85 MB로 128 MiB(134,217,728 B) 안이다. 3088×2069(6,389,072 px)는 높이가 8의 배수가 아니라 블록 행이 하나 늘어 134,309,472 B로 넘는다(표 크기 제외)
- 실측(PR #77 §3.1, jpeg-js 0.4.4, 128 MiB): 3088×2069는 jpeg-js 회계 초과로 거부되고 256 MiB에서는 디코드된다. 제품에서는 우리 추정식(`jpeg-validation.ts:255-258`, 검사는 `:72`)이 먼저 `jpeg_resource_limit`를 낸다
- 바꿀 문안: 회계 절 끝에 한 문장을 더한다

> Because the estimate grows by about 21 bytes per pixel for this 4:4:4 profile,
> the 128 MiB ceiling admits JPEGs up to about 6.39 million pixels (for example,
> 3088×2064 is admitted but 3088×2069 is not). Larger JPEGs return
> `jpeg_resource_limit` even though they are within the 16,777,216 pixel limit.

- 6.12c(JPEG tolerant)가 회계 상한이나 식을 바꾸면 이 문장도 함께 고친다
