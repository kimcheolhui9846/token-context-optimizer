# 이미지 영역 선택기(selector)를 제품에 넣을지: 근거와 선택지

- 작성: Claude Code, 2026-10-16. 상태: **초안, 사용자 결정 대기**
- 문제
  - 확정한 기여 C2는 "이미지는 **질문 인식 crop**, 저해상도 전체 썸네일, 판독 불가 시 원본 재요청으로 다룬다"이다(관련 연구 메모 §5).
  - 그러나 제품 계획 Task 36은 "영역 선택(selector, OCR)은 이번 범위가 아니다. 영역은 입력으로 받는다"이다.
  - 실험 2·3에서 질문 인식 crop을 한 것은 `research/`의 OCR 선택기(`src/selector.mjs`, tesseract.js)다. 플러그인에는 없다.
  - 이대로면 논문의 시스템과 배포 플러그인이 다르다.

## 1. 현재 선택기의 사실관계

| 항목 | 내용 | 출처 |
|---|---|---|
| 방식 | 이미지를 긴 변 4096(최대 4배)까지 키워 OCR → 질문 키워드와 가장 많이 맞는 줄 → 고정 규칙으로 창(window) 생성 | `src/selector.mjs` `createOcr`, `selectWindow`, `SELECTOR_C1` |
| 규칙 | 창 크기·축 행 판정 상수(줄 높이 배수, 25%, 256×128 최소)를 합성 템플릿 파일럿에서 손으로 정했다 | 같음 |
| 언어 | 영어(eng)만. 키워드는 영어 불용어 목록과 3자 이상 토큰 | 같음 |
| 의존성 | tesseract.js 5.1.1 + tesseract.js-core 5.1.1(Apache-2.0). core 30 MB(WASM 변형 여러 벌, 개당 2.9–4.7 MB). 언어 데이터 `eng.traineddata` 5.2 MB는 **첫 실행 때 내려받는다** | `research/node_modules`, `research/.cache` |
| 확대 | `sharp`로 확대한다. 플러그인에는 resize 구현이 없다(Task 33 결정: X8 보류) | `selector.mjs` L19–21, `docs/research/first-transform-jpeg-probe-decision.md` §5(main) |
| 속도 | 이미지당 약 1.4–1.7초(OCR + 확대, i9-12900F 24코어, 2048 원본·1024 축소 각 6장). 언어 데이터 캐시가 있을 때 초기화 0.14초 | 2026-10-16 측정 |
| 플러그인 배포 | esbuild 단일 파일 번들(`bin/token-context-optimizer.mjs`). 의존성과 라이선스 고지를 한 파일에 넣는다 | `scripts/build-bundle.mjs` |

### 성능 (실험 2 held-out 144 slot, 모델 호출 없음)

| 구분 | 창 찾음 | 찾은 것 중 근거 덮음 |
|---|---|---|
| 전체 | 98/144(68%) | 68/98(69%) |
| 기존 레이아웃 / v2 | 50/72 / 48/72 | 38/50(76%) / 30/48(62%) |
| 문서 / 차트 / UI | 39/48 / 35/48 / 24/48 | 27 / 25 / 16 |
| **작은 글자 문항** / 그 밖 | **32/72(44%)** / 66/72 | 24/32 / 44/66 |
| 원본 / 1024 축소+JPEG(combined) | 26/36 / 22/36 | 19 / 14 |

- **crop이 가장 필요한 작은 글자 문항에서 선택기가 가장 약하다**(44%).
- 처음 보는 레이아웃(v2)에서 근거를 덮는 비율이 떨어진다(76% → 62%).
- 대안이었던 모델 기반 위치 찾기(pilot-003 C2, GPT-4o detail low)는 144건 중 65건에서 쓸 수 있는 좌표를 얻지 못했다. 좌표를 얻은 79건 중 근거를 덮은 것은 45건이다. 원인은 구현 문제(형식, 출력 상한)로 진단했다(`results/pilot-003/README.md` §5).

## 2. 선택지

| | 내용 | 장점 | 단점·위험 |
|---|---|---|---|
| **(a) OCR 선택기를 제품에 넣는다** | `research/` 선택기를 플러그인 도구로 옮긴다(예: `query_image_artifact`) | 논문 C2와 제품이 같다 | 의존성 35 MB+, 첫 실행 네트워크 다운로드(오프라인 설치와 충돌), 단일 파일 번들 구조 변경, resize 구현 선행, 영어 전용, 합성 레이아웃에 맞춘 상수, 작은 글자 44%. 큰 Task(C 등급 여러 개) |
| **(b) 호출자(에이전트 모델)가 영역을 정한다** | 제품은 crop 도구 + overview(Task 36)만 둔다. 에이전트가 overview를 보고 좌표를 넘긴다 | 의존성 없음. 실제 사용 환경의 모델(Codex·Claude Code의 상위 모델)이 영역을 고른다 | 실험 근거가 약하다(C2 파일럿은 구현 문제로 실패). 실험 2·3의 선택기와 다른 경로라 논문 결과가 제품 경로를 직접 검증하지 않는다 |
| **(c) 혼합: 제품 기본은 (b), OCR 선택기는 선택 설치 모듈로 나중에** | Task 36 그대로. 논문은 "실험에서는 OCR 선택기가 호출자 역할을 했다"고 밝히고, C2 문장을 그 범위로 조정한다 | 지금 일정과 범위를 지킨다. 논문이 정직해진다. OCR 모듈은 근거가 쌓이면 추가한다 | C2 문장을 다시 고쳐야 한다. "질문 인식 crop이 제품 기능"이라고 말할 수 없다 |

## 3. 권장: (c)

1. **(a)는 지금 근거로 정당화하기 어렵다.** 작은 글자 44%, 새 레이아웃 62%다. 이 정도면 플러그인 기본 기능으로 내놓기에 약하고, 의존성·배포 비용이 크다.
2. **(b)만 하면 논문과 제품의 연결이 끊긴다.** 실험 2·3은 OCR 선택기로 측정했다.
3. **(c)는 사실대로 말한다.** 논문의 측정 대상은 "원본 보존 + crop 도구 + 원본 재요청이라는 규칙 묶음"이다. 실험에서 영역은 연구용 OCR 선택기가 정했다고 밝힌다. 제품은 같은 도구를 주고 영역 선택은 호출자에게 맡긴다.
4. **C2 수정안:** "텍스트 에이전트에서 제안된 원본 보존·재조회 구조 [A1, A2]를 이미지 입력으로 확장한 MCP 플러그인. 이미지는 원래 해상도 영역 crop, 저해상도 전체 썸네일, 원본 재요청으로 다룬다. 영역은 호출자가 정하며, 실험에서는 OCR 기반 질의 인식 선택기를 호출자로 사용했다."
5. **후속(선택):** 호출자 모델이 overview를 보고 영역을 고르는 경로를 작은 실험으로 확인한다. 예: 구조화 출력으로 고친 C2를 실험 2 calibration 세트에 적용한다. 지금 일정에는 넣지 않는다.
