## 1. 지금 동작 (main `8a149b0`)

### 1.1 노출되는 형태

`classifyContext`가 `semantic`을 내려면 **모든 줄이 문장**이어야 한다(`isPositiveSemanticLine`: 글자 비율 ≥ 0.6, 단어 ≥ 5, `.!?`로 끝남, 대문자 약어·기술 토큰 없음). 그래서 노출은 아래 경우에 생긴다.

| 형태 | 예 | 지금 |
|---|---|---|
| 라벨 줄이 따로 있음 | `비밀번호: hunter2` (단독 또는 한국어 산문 줄과 함께) | `unknown` (압축 금지 경고) — 노출 아님 |
| **문장 안의 라벨과 문자 값** | `회의실 와이파이 비밀번호: hunter2 이니까 접속할 때 참고해 주세요.` | **`semantic` (손실 압축 허용)** |
| 문장 안의 라벨과 숫자 값 | `고객센터에서 받은 OTP: 482913 을 입력하면…` | `exact` — 숫자 규칙(`numeric_or_table`)이 우연히 보호 |
| 대문자 약어가 든 문장 | `회의실 API 키: hunter2 이니까…` | `unknown` — 대문자 약어 때문에 semantic이 안 됨 |
| 같은 문장, 영어 라벨 | `… password: hunter2 …` | `exact` (`secret`) |

- `비밀번호`, `비번`, `암호`, `패스워드`, `인증키`, `개인키`, `토큰`, `인증 토큰`, `복구 코드`, `계정 비밀번호`가 `:`·`=`·`：` 어느 구분자로든 문장 안에 있으면 지금 모두 `semantic`이다(결과 `matrix`)
- N-17 처음 기록의 "산문과 함께 있으면 semantic"은 **같은 문장 안**일 때만 맞다. 라벨 줄이 산문 줄과 따로 있으면 `unknown`이다

### 1.2 영어 규칙과의 짝

- 영어 규칙(#0: `password|secret|token|api key|private key` 등 + F-21 E-3 자격증명 라벨)은 `[:=]` 구분자만 본다
- 영어도 지키지 않는 형태가 둘 있다. 이번 설계의 경계를 정할 때 기준으로 삼는다
  - 서술형: `The guest wifi password is hunter2 …` → `semantic`
  - 전각 콜론: `Guest wifi password：hunter2 …` → `semantic` (**새 발견**, §5)

## 2. 후보 규칙

- 라벨 뒤에 `[ \t]*`, 그다음 `:`·`=`·`：`(U+FF1A)가 오면 `secret`으로 본다
- 한글 라벨은 왼쪽 경계를 두지 않는다. `계정비밀번호:`처럼 붙여 쓴 복합어도 잡기 위해서다. `api 키`만 영문 앞 경계(`(?<![A-Za-z0-9])`)를 둔다
- 라벨 안 띄어쓰기는 공백·탭 한 칸만 허용한다. 라벨 안 하이픈·밑줄은 따로 허용하지 않는다. 다만 한글 라벨에 왼쪽 경계가 없어서, **끝이 T2 라벨이면 그 접미부가 걸린다.** 결과 `boundaries`로 확인했다(2026-11-02 Codex 지적으로 고침)
  - 걸림(T2 `토큰:` 접미부): `인증_토큰:`, `인증-토큰:`, 그리고 비밀이 아닌 `입력토큰:`
  - 안 걸림: `API-키:`, `개인_키:`, `비밀_번호:`, `보안_코드:` (`키:`, `번호:`, `코드:`는 라벨이 아니다)
  - 따라서 T1만 쓰느냐 T1+T2를 쓰느냐에 따라 하이픈·밑줄 표기의 보호 범위가 달라진다. 구현 oracle은 두 경우의 기대값을 따로 둔다
- `api 키`는 영숫자가 바로 앞에 붙으면(`v2api 키:`) 걸리지 않고, 한글·밑줄 뒤(`카카오api 키:`, `my_api 키:`)에서는 걸린다. 영어 `\b`와 경계가 다르다
- 구분자 앞 공백은 `[ \t]*`다. 그래서 `비밀번호+U+00A0+:`(NBSP), `비밀번호+U+3000+:`(전각 공백)은 걸리지 않는다. 영어 #0·E-3은 라벨 뒤에 `\s*`를 써서 `password+U+00A0+:`이 이미 exact다. 즉 후보가 영어보다 좁다(K-6)
- `**비밀번호**:`처럼 마크다운 강조가 라벨과 구분자 사이에 있으면 걸리지 않는다. 현재는 문장 안이면 semantic이다(K-7)
- 라벨 바로 뒤가 구분자여야 하므로 `암호화:`, `토큰화:`, `비밀번호 변경:`은 걸리지 않는다(결과 `mustNotMatch` 3건 모두 불일치 확인)

| 묶음 | 라벨 | 성격 |
|---|---|---|
| T1 | 비밀번호, 비번, 패스워드, 인증키, 개인키, 비밀키, 시크릿 키, 액세스 키, API 키, 복구 코드, 백업 코드, 인증 토큰, 접근 토큰, 액세스 토큰 (띄어쓰기 한 칸 허용) | 자격증명 말고는 거의 쓰이지 않는다 |
| T2 | 암호, 토큰, 보안 코드 | 다른 뜻도 흔하다(cipher, 언어 모델 토큰, 카드 CVC 설명) |

## 3. 영향 조사

### 3.1 저장소 한국어 문서

- 대상: 추적 중인 한글 포함 Markdown 114개, 고유 단위 14,188개(줄 + 빈 줄로 나눈 문단)
- T1에 걸린 단위: **0**
- T2에 걸린 단위: 10. 이미 `exact`가 8, `unknown → exact`가 2. 둘 다 용어 정의 줄이다(`공급자 청구 토큰 = provider-billed tokens`, `이미지 토큰 = …`)
- `semantic → exact`로 바뀐 단위: **0**
- 한계: 이 말뭉치는 우리 기술 문서라 실제 사용자 대화와 다르다. 대화체 과보호는 아래 직접 예로만 확인했다

### 3.2 과보호 예 (후보 규칙이 exact로 만들 문장)

- `암호: 이 장에서는 … 암호의 역사를 …` (T2), `토큰: 언어 모델이 … 기본 단위를 말한다.` (T2), `비밀번호: 영문과 숫자를 섞어 여덟 자 이상으로 …` (T1)
- 결과는 `exact`, 즉 압축하지 않는 쪽이다. 정보가 사라지지 않고 압축 이득만 줄어든다
- 영어도 같은 선택을 했다. F-21 E-2에서 `secret`을 유지하고 `Pass: the ball to Jim`의 과보호를 받아들였다. 영어 #0에는 `token:`도 이미 있다
- 왼쪽 경계가 없어서 `입력토큰:`처럼 비밀이 아닌 합성어도 문장 안에서 semantic → exact가 된다. 저장소 말뭉치에서 semantic 전환이 0이라는 것은 대화체 과보호가 0이라는 뜻이 아니다

### 3.3 속도 (참고값, 게이트 아님)

- 후보 정규식 단독, 5회 중앙값(2026-11-02 재생성 값): 띄어 쓴 라벨 반복 8.2 MB 12.3 ms, `비밀` 뒤 탭 반복 5.2 MB 10.2 ms, 한국어 산문 8.7 MB 8.7 ms. 시간은 실행마다 조금씩 다르다(Codex 재현 12.3/9.7/8.7 ms)
- 같은 입력에서 `classifyContext` 전체는 756–1,269 ms다. 후보 정규식 단독 시간과 기존 분류 1회 시간의 비는 약 1%다. 통합 뒤의 실제 추가 시간은 아니다
- 탭 반복 입력은 `비밀` 뒤에 탭이 있어서, **완성된 라벨 뒤 긴 공백**은 검증하지 않았다. K-6에서 `\s*`를 고르면 이 형태가 최악 입력 후보가 된다(§6)
- 최종 판정은 구현 PR의 성능 게이트로 한다. 그때 #85(`research/plans/2026-11-02-perf-gate-noise.md`)의 G-1–G-6을 적용한다

## 5. 새로 찾은 것

- **N-27(제안): 영어 자격증명 라벨 + 전각 콜론(`password：hunter2`)이 문장 안에 있으면 semantic이다.** 영어 #0과 E-3의 구분자가 `[:=]`뿐이라서다. N-17과 같은 종류지만 영어 규칙을 바꾸는 일이므로 따로 둔다. N-17 구현과 같은 PR에 넣을지는 계획 PR에서 정한다

## 6. 구현 PR에 넘길 조건 (Codex)

1. 계획 PR 먼저 낸다. K-1–K-8 결정과 영향 조사(F-21처럼 기존 입력 전체에서 모드가 바뀌는 행 수)를 담는다
2. 테스트는 독립 oracle로 한다. 라벨 × 구분자 × (줄 단독, 문장 안) 행렬을 둔다. 음성 사례 `암호화:`·`토큰화:`·`비밀번호 변경:`·서술형을 함께 둔다. 결과 `boundaries`의 13개 경계 사례를 K-1·K-6–K-8 결정에 맞춘 기대값으로 넣는다. T1만/T1+T2 기대값은 따로 둔다. 기존 영어 기대값은 불변이어야 한다
3. 넣는 방식은 F-21과 같다. 기존 #0의 `/iu` 정규식과 E-3의 `/i` 정규식은 그대로 두고 새 술어만 OR로 붙인다. tuple 번호, `reasons` 중복 제거와 순서가 바뀌지 않는지 회귀 테스트한다
4. 성능: 10 MiB 근처 최악 입력을 넣는다. 띄어 쓴 라벨 반복과, **완성된 라벨 뒤 긴 공백(K-6이 `\s*`면 NBSP·줄바꿈 포함) 뒤 구분자 없음**을 넣는다. #85의 G-1–G-6을 적용한다
5. 문서: 정책 설명에 한국어 라벨과 한계(서술형 미보호, 숫자 값은 숫자 규칙이 보호, K-7·K-8에서 뺀 표기)를 적는다
6. `api` 앞 경계를 영어 `\b`와 맞출지 계획 PR에서 정한다
