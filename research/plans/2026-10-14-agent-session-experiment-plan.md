# 실험 3 계획 — 다중 턴 에이전트 세션의 원본 보존형 발췌 대 compact

- 작성: Claude Code(관장), 2026-10-14. 상태: **제안(사용자 승인 전)**. 승인 뒤 개발 세트로 하네스를 만들고, held-out 전에 프로토콜을 사전 등록한다.
- 연결: [논문 틀 수정안](./2026-10-14-paper-framework-revision.md)의 RQ3. 실행 담당은 Claude(`research/`)다.

## 1. 질문과 가설

RQ3: 다중 턴 에이전트 세션에서 원본 보존 발췌(텍스트·이미지)는 전체 유지와 compact에 비해 누적 청구 토큰과 과제 정확도를 어떻게 바꾸는가?

| 가설 | 내용 | 비교 |
|---|---|---|
| H1 | 플러그인은 전체 유지보다 누적 입력 토큰이 적고, 정확도는 크게 떨어지지 않는다 | S2 대 S0 |
| H2 | compact는 토큰을 줄이지만, 앞 턴에 나온 정확한 세부(작은 글자, 로그 줄)를 늦은 턴에 회상하는 정확도가 떨어진다 | S1 대 S0 |
| H3 | 플러그인을 compact와 함께 쓰면 compact의 절감을 유지하면서 늦은 턴 회상을 되찾는다 | S3 대 S1 |
| H4 | 공급자 프롬프트 캐싱이 켜져 있으면 발췌의 토큰 이점은 줄지만 사라지지 않는다 | 캐시 기준 대 정가 기준 |

"크게 떨어지지 않는다"의 기준(margin)은 사전 등록 전에 사용자가 정한다. 정하기 전 결과는 탐색 결과로만 보고한다.

## 2. 세션 설계

각 세션은 에이전트가 작업 중에 아티팩트(스크린샷, 문서 이미지, 로그)를 받아 가며 질문에 답하는 고정 대본이다.
실제 에이전트처럼 스스로 행동을 계획하지 않고, 사용자 턴이 정해져 있다. 이 차이는 한계로 적는다.

### 2.1 템플릿 3종

| 템플릿 | 아티팩트 | 시나리오 |
|---|---|---|
| UI 디버깅 | 설정 화면 스크린샷, 대시보드 스크린샷, 오류 로그(텍스트, 약 2,500토큰) | 상태 표시와 로그를 대조해 원인을 찾는다 |
| 문서 검토 | 청구서 이미지, 공지 문서 이미지, 처리 기록 로그(텍스트) | 금액·참조 코드를 확인하고 기록과 대조한다 |
| 리포트 점검 | 막대 차트, 선 차트, 작성 메모(텍스트) | 수치와 메모가 일치하는지 확인한다 |

이미지는 pilot의 생성기(작은 글자 13–14px 포함)를 쓰고, 로그와 메모는 결정적 생성기로 새로 만든다.
정답과 근거 위치(이미지 상자, 로그 줄 번호)는 생성 시점에 기록한다.

### 2.2 턴 구성 (8턴)

| 턴 | 동작 | 질문 유형 |
|---|---|---|
| 1 | 아티팩트 1(이미지) 제시 | 즉시 세부(작은 글자) |
| 2 | 아티팩트 2(로그) 제시 | 즉시 세부(특정 오류 줄) |
| 3 | 아티팩트 3(이미지) 제시 | 즉시 세부 |
| 4 | 새 아티팩트 없음 | 교차(로그 줄 + 이미지 값) |
| 5 | 새 아티팩트 없음 | 요지(전체 상황 요약형, 정답은 핵심어 포함 여부) |
| 6 | 새 아티팩트 없음 | **늦은 회상**: 턴 1 이미지의 작은 글자 |
| 7 | 새 아티팩트 없음 | **늦은 회상**: 턴 2 로그의 정확한 줄 |
| 8 | 새 아티팩트 없음 | 교차 + 늦은 회상 |

늦은 회상(턴 6–8)이 compact의 손실을 드러내는 핵심 문항이다. 요지 문항(턴 5)은 compact가 잘하는 쪽을 공정하게 넣은 것이다.

## 3. 조건

| 조건 | 컨텍스트 처리 |
|---|---|
| S0 전체 유지 | 아티팩트를 나올 때 컨텍스트에 그대로 넣고(이미지는 원본, 로그는 전문), 대화 전체를 계속 보낸다 |
| S1 compact 모사 | S0과 같다. 다만 누적 컨텍스트가 임계값을 넘으면 고정 compact 지시문으로 같은 모델이 이전 대화를 요약하고, 요약으로 대체한다. 요약 뒤에는 이미지가 남지 않는다 |
| S2 플러그인 | 아티팩트를 컨텍스트에 넣지 않고 카드(ID, 종류, 제목, 크기)만 넣는다. 모델은 도구로 필요한 부분을 가져온다(§4). 발췌로 판독할 수 없으면 원본을 요청한다 |
| S3 플러그인 + compact | S2에 S1의 compact를 더한다. compact 지시문은 아티팩트 ID를 요약에 남기게 한다. 아티팩트는 밖에 남아 다시 발췌할 수 있다 |
| S4 단순 축소 유지(보조) | S0과 같되 이미지를 arm 변환(긴 변 1536 → q75)으로 넣는다. RQ1의 회계 결과가 세션에서 어떻게 나타나는지 보는 보조 조건 |

- compact 임계값과 요약 길이 상한은 calibration에서 정하고 held-out 전에 고정한다.
- 이 compact는 제품(Claude Code, Codex)의 compact가 아니다. 공개 규칙으로 재현한 모사다.
- 모든 조건이 같은 system 지시, 같은 질문, 같은 모델, 같은 출력 상한을 받는다. 판독 불가 표지("UNREADABLE")도 모든 조건에 같게 준다.

## 4. 플러그인 조건의 도구 (S2, S3)

| 도구 | 동작 | 구현 |
|---|---|---|
| `query_text_artifact(id, query)` | 질의와 맞는 줄을 줄 번호와 함께 최대 N줄 돌려준다 | 실제 플러그인의 `query_artifact`를 MCP(stdio)로 호출하는 것을 권장. 실험과 실제 플러그인을 직접 잇는다 |
| `query_image_artifact(id, question)` | 질문에 필요한 영역을 원래 해상도로 잘라 arm 변환 후 돌려준다. 출처(원본 해시, crop 좌표)를 함께 준다 | 플러그인에 아직 없으므로 `research/`의 C1 selector로 모사한다. 이 인터페이스가 향후 플러그인 도구의 시안이다 |
| `get_original_image(id)` | 배정 원본을 그대로 돌려준다 | 발췌로 판독할 수 없을 때 쓰도록 system 지시에 적는다(응답 기반 fallback의 세션판) |

- 턴당 도구 호출 상한: 3회(calibration에서 확인 후 고정).
- 도구 결과(발췌 이미지, 로그 줄)도 대화 기록에 남는다. 이것도 누적 토큰에 포함된다.

## 5. 지표

| 구분 | 지표 | 비고 |
|---|---|---|
| 주 지표(효율) | 세션당 누적 입력 토큰 | 모든 호출(도구 루프, compact 요약 호출 포함)의 합. 정가 기준과 캐시 기준을 따로 보고 |
| 주 지표(정확도) | 문항 내용 정확도의 세션 평균 | pilot과 같은 채점(엄격 / 내용 일치) |
| 핵심 보조 | 늦은 회상 정확도(턴 6–8) | H2, H3 판정 |
| 보조 | 비용(정가), 출력 토큰, 도구 호출 수, 원본 요청률, compact 횟수, 지연, 실패 수, 조용한 오답 수 | |

분석은 세션 단위로 짝지어 한다(같은 세션을 모든 조건에 적용). 조건 간 차이는 세션 단위 차이의 분포로 보고한다.

## 6. 데이터 분할과 규모

| 분할 | 세션 수 | 쓰임 |
|---|---|---|
| 개발(dev) | 3(템플릿당 1) | 하네스 구현과 시험. 결과를 보고 고쳐도 된다 |
| calibration | 6(템플릿당 2) | compact 임계값, 요약 길이, 도구 상한 고정 |
| held-out | 24(템플릿당 8) | 사전 등록 뒤 한 번 실행 |

- 세션 하나가 family 하나다. 분할 간 seed를 겹치지 않는다.
- 템플릿을 분할 간에 공유하면 결과가 낙관적일 수 있다. held-out에 새 템플릿 변형을 둘지는 사용자 결정 사항이다(§9).
- 실험 2의 calibration·held-out family와도 겹치지 않게 한다.

## 7. 캐싱 처리

- OpenAI: 자동 캐싱이 꺼지지 않으므로 응답 usage의 캐시 토큰 필드를 기록한다. 필드 이름과 할인율은 실행 전에 공식 문서로 확인한다 [검증 필요].
- Anthropic: 캐싱은 명시적이다. 모든 조건에 같은 규칙으로 고정 접두부에 캐시 지점을 둔다. 캐시 쓰기와 읽기 토큰을 따로 기록한다 [검증 필요].
- 보고: 정가 기준(캐시 무시)과 캐시 기준(공급자 청구 방식)을 모두 보고한다. 결론은 둘 중 보수적인 쪽으로 쓴다.

## 8. 비용 추정 (정가, 캐싱 무시 상한, 실행 전 추정)

- S0 한 세션: 매 턴 이미지 최대 2장 + 로그 약 2,500토큰 + 대화가 누적된다. GPT-4o 기준 약 3–4만 입력 토큰이다.
- 5개 조건 합계: 세션당 약 10–12만 토큰, GPT-4o 약 $0.3.
- held-out 24 + calibration 6 + dev 3, 재실행 여유 포함 GPT-4o 약 $10–15. Haiku(이미지 토큰은 더 많고 단가는 낮음) 약 $5–10.
- 합계 약 $15–25. 현재 예산 상한($20, 실행마다 적용)은 실행별로는 충분하다. 공급자 두 곳의 전체 합계는 사용자 승인을 받는다.

| 단계 | 산출물 | 비고 |

| 1 | `src/sessions.mjs`: 세션 생성기(이미지는 기존 생성기, 로그·메모는 새 결정적 생성기), 정답·근거 위치 기록 | 개발 세트 3개 생성 |

## 10. 위험과 대응

| 위험 | 대응 |
|---|---|
| 모사 compact가 제품과 다르다 | 지시문·임계값을 공개하고 결론을 "손실 요약형 compact 일반"으로 한정 |
| 도구 호출 행동이 흔들린다 | temperature 0, 고정 지시, 호출 상한, 호출 수 보고. 같은 세션 반복 실행 여부는 calibration에서 판단 |
| 캐싱으로 절감이 작게 나온다 | 그대로 보고(H4). 정가 기준만으로 결론 내지 않음 |
| 대본형 세션이 실제 에이전트와 다르다 | 한계로 명시. 후속으로 실제 에이전트 로그 재생 실험 제안 |
| 플러그인 MCP 연결이 실패한다 | 텍스트 도구를 같은 규칙의 `research/` 구현으로 대체하고 기록 |
| 범위가 커진다 | dev → calibration 순서로 작게 시작. held-out 규모는 calibration 뒤 다시 확인 |

## 11. 사용자 결정 필요

1. 실험 3을 이 설계로 진행할지. 개발 세트 하네스 구현은 승인 즉시 시작할 수 있다(비용 약 $1 이내).
2. H1의 정확도 margin(예: 내용 정확도 차이 −5%p 이내). held-out 전에만 정하면 된다.
3. held-out에 새 템플릿 변형을 둘지. 리뷰어 의견: 템플릿당 변형 하나를 held-out 전용으로 둔다.
4. 텍스트 도구를 실제 플러그인 MCP로 연결할지. 리뷰어 의견: 연결한다. 논문의 C2(시스템)와 실험을 직접 잇는다.
5. 공급자 두 곳의 전체 예산(약 $15–25).

## 12. 사용자 결정 (2026-10-15)

사용자가 이 계획을 전부 승인했다(§11의 1–5).
1. 이 설계로 진행한다. 개발 세트 하네스부터 구현한다.
2. H1 margin은 리뷰어 예시(내용 정확도 차이 −5%p 이내)를 기본안으로 둔다. held-out 사전 등록 때 확정한다.
3. held-out에 템플릿당 새 변형 하나를 전용으로 둔다.
4. 텍스트 도구는 실제 플러그인 MCP로 연결한다.
5. 예산은 공급자 두 곳 합계 약 $15–25다. API 호출 비용만 해당하며 GPU(RunPod)는 쓰지 않는다.

## 13. 개발 단계 뒤 결정 (2026-10-15)

- 사용자 결정: S1·S3의 compact는 **턴 3과 턴 6 뒤의 고정 일정**으로 한다. 임계값(4,000 prompt tokens)을 넘은 턴 수는 "임계값 방식이었다면 compact했을 횟수"로 보조 보고한다.
- 개발 단계에서 고정한 규칙(calibration 전 동결)은 세 가지다.
  - 도구 결과 이미지 비우기(EVICT)
  - 플러그인 조건의 UNREADABLE 시 원본 자동 재요청(AUTO_ORIGINAL)
  - 채점 규칙: yes/no·on/off 정확 일치, 숫자 단독 일치, 월 약어 허용
- 세부와 근거는 [개발 단계 결과](../results/s3-dev-002/README.md)에 있다.
